# Android Windows worker-stall qualification

## Scope and authority

This implements the positive worker-recovery gate of the confirmed [Flutter contract](../design/VOD_FLUTTER_CLIENT_MIGRATION.md), following the [response-loss checkpoint](ANDROID_PLAYBACK_QUALIFICATION.md#october-30-attachment-and-accepted-response-loss-checkpoint). It changes qualification mechanics, not product policy. Work stays on main with locked dependencies and no release. Normal production attachment/caps, decoder evidence, ambient/offline/iOS and remaining relay/scope gates stay separate.

Capture the actual spawned FFmpeg child ID, exact source/manifest/arguments and a retained Windows process handle before handing it into the existing worker owner. Any capture refusal must still hand off, terminate and observe the spawned child before failing preparation. No process-name search, arbitrary PID input, production fault route, synthetic failure label or shortened watchdog is permitted.

A Windows-only test module pins bounded canonical source/executable files read-only, rejects reparse points and checks content/identity. Only the selected owned source receives the existing readrate arguments. Configure its manager before cloning AppState into the router. Bound retained spawn observations to four. An opened process handle must match the pinned image and actual parent, retain creation identity and remain alive around validation. A bounded ToolHelp snapshot filters threads by process; each opened thread must independently report the same owner. Suspend each target thread once, refuse prior suspension after undoing the added increment, and repeat finite enumeration until stable. Retain thread handles and resume only owned increments on abandonment. No host privilege, service, OS feature or resource-limit changes are needed.

The worker uses a separately authored forty-second source, copied from the controlled eight-second reference without a codec change and independently probed on the host and server. It remains below the existing sixteen-MiB bound. The eight-second picture-reference stages remain unchanged. The worker is frozen immediately after first usable output. Android must initialize and report a real source-position checkpoint before the existing thirty-second no-progress deadline expires. The watchdog must physically terminate the process, complete stderr observation and produce Stalled through the normal lifecycle. Only then can existing positive server evidence and the retained checkpoint authorize the client's recovery command. The original eight-second worker source exited at the startup boundary; its failed attempts are preserved below. Increasing only the owned source duration gives the guard a live process after readiness without shortening the watchdog or extending any observer. Never fabricate checkpoint or failure evidence.

The native journey must preserve one viewer/history, prove one recovery and a fresh output revision, continue from confirmed source position, preserve tracks/quality/play intent, and confirm local/server/root cleanup. The server separately verifies process exit, failure classification, checkpoint-before-retirement, recovery budget, operation count and final release. Existing observer, lease, relay, root, VM, PostgreSQL, encoder and scenario budgets remain unchanged.

## Official research — October 30, 2026

URLs were discovered through MCP search. Microsoft describes [SuspendThread](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-suspendthread) as debugger-oriented and warns against synchronization with suspended threads. Use it only for an isolated child fault fixture; the test must not acquire synchronization objects from the target. [ToolHelp snapshots](https://learn.microsoft.com/en-us/windows/win32/api/tlhelp32/nf-tlhelp32-createtoolhelp32snapshot) require owned handle closure and thread-owner filtering; [thread enumeration](https://learn.microsoft.com/en-us/windows/win32/api/tlhelp32/nf-tlhelp32-thread32first) requires correct structure sizing and explicit end/error handling. [Process handles and identifiers](https://learn.microsoft.com/en-us/windows/win32/procthread/process-handles-and-identifiers) support retaining object identity rather than authorizing later action from a numeric PID alone.

[FFmpeg's readrate documentation](https://www.ffmpeg.org/ffmpeg-all.html) supports controlled file pacing. [Rust Windows OpenOptionsExt](https://doc.rust-lang.org/stable/std/os/windows/fs/trait.OpenOptionsExt.html) exposes sharing flags for read-only pinning. Use stable APIs on Rust 1.99.1; avoid nightly metadata methods. Existing client recovery/status semantics remain governed by the [W3C status-message guidance](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html): report preparation, recovery and uncertainty truthfully without claiming success early. No spoken-accessibility claim follows from this native fault test.

| Approach | Pros | Cons |
| --- | --- | --- |
| Small test-only Kernel32 bindings | No dependency/lock change; exact retained handles; native Windows backend | Requires careful ABI, error and cleanup review |
| Direct declaration of locked windows-sys | Generated typed API declarations | Adds a server dependency edge/features for this isolated fixture |
| Linux backend plus Windows emulator | Reuses existing pidfd/SIGSTOP fixture | Introduces cross-host lifecycle, IPC and networking ownership |

Recommendation stack: existing locked Rust/Tokio process owner and watchdog; bounded Windows test-only file/process/thread handles; existing FFmpeg pacing; existing protocol-two Flutter/Media3/relay; managed isolated Android plus real PostgreSQL/HTTP/FFmpeg. Prefer the small test-only Windows adapter for this gate; reassess a typed dependency if production Windows API use grows.

A later server failure does not trigger another native callback. Generic errors remain neither worker proof nor decoder proof.

The next recommended item is a modular, bounded positive-worker-evidence observer under the existing [design review](../../CONTEXT.md#design-review-with-grill-me): bind exact session/profile/start/output, retain ownership until reads finish, preserve independent lease renewal, and submit at most one fresh recovery only after current server eligibility and the confirmed checkpoint. Compare immediate manual recovery (smallest state machine, no observation traffic) with bounded metadata observation (preserves the agreed automatic recovery but adds cancellation/deadline ownership). The proposed sixty-second/one-second observation policy requires confirmation before implementation; it must not change the watchdog, infer decoder proof, replay mutations, create a new Start or relax any existing lease/root/resource limit. Native ambient and production attachment/caps remain blocked by the overall Android gate.
