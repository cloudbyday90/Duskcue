## Scope and confirmed decisions

This October 18, 2026 increment follows [reference format qualification](PLAYBACK_FORMAT_QUALIFICATION.md). It enables only independently qualified SDR H.264, HEVC and AV1 routes in the existing web and desktop Player. The user confirmed the scope through the repository grill-me review, including positive support **and** smoothness as admission requirements, power efficiency as an independent diagnostic, and observations retained only in memory for the current playback attempt. File or track changes require another bounded check.

Retain Rust/Axum, managed FFmpeg, Svelte/ES modules, hls.js and Tauri/WebView2. JavaScript tooling uses `.mjs`; no CommonJS, new engine, branch, release or device-profile persistence is introduced. Unsupported HDR conversion retains HTTP 422 `PLAY_020`. Native source-error code 4, network/authentication failures, HDR passthrough/conversion, general Opus-to-HLS copying, structured scanner cancellation and broader damaged-media qualification remain outside this increment.

Rust remains responsible for the server and native integration. Existing JavaScript/TypeScript stays in the shared client and tools; `.mjs` is an explicit JavaScript ES-module extension, rather than another language or service layer. This increment does not require a broad client language rewrite.

## Research and recommendations

Official URLs are discovered and opened through connected MCP research tools. The [Media Capabilities working draft](https://www.w3.org/TR/media-capabilities/), opened October 18, distinguishes `file` and `media-source` configurations and reports support, smoothness and power efficiency separately. These are predictions about the supplied configuration, rather than authorization or a guarantee of successful playback. Query only the actual server-proposed source/delivery configurations; avoid enumerating an entire device capability space.

The [MSE working draft](https://www.w3.org/TR/2026/WD-media-source-2-20260807/) calls for precise codec parameters in support checks. Baseline hls.js/MSE support cannot establish a particular source codec's support. The completed corpus already demonstrated differing file and MSE predictions; desktop bearer transport must retain authenticated HLS rather than adopting a cookie-only native-file route.

[FFmpeg format documentation](https://ffmpeg.org/ffmpeg-formats.html) distinguishes stream copying from encoding and describes fragmented-MP4 HLS. Source-file and remuxed-output codec configurations must remain distinct. The previous Opus corpus exposed an end-padding discrepancy before aligned fixture authoring corrected it; that fixture does not qualify arbitrary Opus packetization through MP4/HLS. Prefer validated compatible AAC handling for this increment's copied-video HLS.

[RFC 6381](https://www.rfc-editor.org/rfc/rfc6381.html), the [HEVC registration](https://www.w3.org/TR/webcodecs-hevc-codec-registration/) and [AV1 binding](https://aomediacodec.github.io/av1-isobmff/v1.3.0.html#codecsparam) define configuration-specific identifiers. Derive these from actual validated avcC/hvcC/av1C records; profile names alone are insufficient. Initial parsing covers ordinary 4:2:0 eight- and ten-bit configurations; absent, raw Annex B/OBU, unsupported or malformed configurations remain conservative. Validated AAC-LC AudioSpecificConfig establishes `mp4a.40.2`; an `aac` label alone does not establish LC. See the [AAC registration](https://www.w3.org/TR/webcodecs-aac-codec-registration/).

## Server contract and ownership

Provide an authenticated, versioned preparation endpoint alongside Start. Reuse authorization, healthy-file selection, selected global stream resolution and quality/force-policy normalization. Preparation allocates neither a play session nor a worker. Return only a finite ordered set of server-authored delivery candidates and exact bounded configurations, with an opaque source/candidate fingerprint. Do not expose filesystem paths, raw decoder configuration or FFmpeg arguments.

Bind the fingerprint to protocol version, authenticated user/profile, source identity and probe revision, selected video/audio/subtitle tracks, actual authenticated transport, delivery, quality and bitrate/force limits. Credential transport follows the same cookie-before-bearer selection as authentication. Start reauthorizes and recomputes this context before using a matching typed observation. Client observations are routing hints within server policy, never credentials or arbitrary processing instructions. Preserve unknown/absent protocol and legacy device-profile behavior.

Native-file delivery is eligible only where the actual transport, container and native track selection can preserve the requested experience. Explicit server-mapped audio/subtitles continue to require server delivery. Bearer clients receive only authenticated MSE/HLS candidates. A video-copy candidate's audio handling and output configuration must match the actual compiled plan; source Opus support does not imply Opus remux correctness.

This first increment optimizes Auto only. Manual and Maximum retain their existing quality behavior. Require known BT.709 primaries, transfer and matrix with limited range for optimized SDR routes; unknown color or wide-gamut SDR retains conservative playback until independently qualified. Capabilities do not establish physical display fidelity. Bind seek limits to the scanned precise duration, rather than the rounded library runtime, and reauthorize/revalidate the admitted source under the play-session lock before replacing a negotiated generation.

Store only accepted immutable source/route context necessary for generation-aware seek and recovery. Do not persist raw browser capability observations as a reusable device profile. Source/candidate equality establishes revision binding; do not pretend a client timestamp enforces expiry.

The version-one wire contract is:

| Operation | Fields and bounds |
| --- | --- |
| `POST /api/v1/playback/prepare` | Existing Start selection and quality fields plus `capability_protocol: 1`; returns `protocol`, 64-character `source_revision` and at most three ordered `candidates` |
| Candidate | `id`: `native_file`, `hls_video_copy_audio_copy` or `hls_video_copy_aac`; `delivery`: `file` or `hls`; `configuration` uses Media Capabilities `type`, `video` and `audio`, including precise `contentType` |
| Start observation | `source_capabilities: {version: 1, source_revision, observations}`; each has `candidate_id`, `status`, nullable `supported`, `smooth`, `power_efficient` and `delivery_supported` |
| Accepted route | Optional `source_route: {candidate_id, source_revision}` in session responses; raw observations are not retained |
| Decoder fallback | Optional `copy_fallback` contains the current generation and exact compatible video/audio descriptor; heartbeat acknowledges that generation with positive `supported` and `smooth` |
| Seek | Requested absolute `position_ms` and actual `stream_offset_ms` identify the presentation position within the replacement HLS timeline |

Observation statuses are `reported`, `unavailable`, `rejected` and `timed_out`. Unknown protocol versions retain conservative behavior. The client allows four seconds for prepare and observations together, with a 1.5-second aggregate observation bound and at most three concurrent exact queries. Cancellation and authorization errors retain their existing behavior.

## Source descriptors and prerequisite hardening

Extend bounded scanner metadata with validated codec sample-entry/configuration information. Derive RFC 6381 identifiers from authoritative configuration data, including required profile, constraint, tier, depth and color distinctions. Preserve provenance and unknown values; do not invent exact bitrate or codec identities. Raw configuration stays outside the public API and database where a small validated descriptor/digest suffices.

Keep existing process output, timeout and concurrency bounds. Optional configuration enrichment must not turn an otherwise usable file into an unhealthy file when attachments or malformed configuration exceed its bounds. Bind the descriptor to stable scanned bytes and verify current opened-file size/mtime against the scan identity before offering an optimized route. Correct modified-file and quick/full scheduling behavior needed for descriptor freshness. Legacy/missing/stale exact descriptors retain conservative behavior; no new playback-time ffprobe is added.

Optional enrichment shares a five-second aggregate execution deadline, four-MiB stdout and 64-KiB stderr ceilings; each decoded configuration is at most 64 KiB. The scanner admits two concurrent probes per scan-path invocation, rather than globally. Ordinary five-/twelve-second probe attempts have separate budgets, and post-kill waiting is outside those execution timers. Persist validated descriptors and configuration digests, not raw extradata. Source freshness uses opened-file size and precise mtime, with database comparisons at PostgreSQL microsecond precision. This metadata identity is not a cryptographic hash of the complete media file.

Replace whole-file/range buffering with one authorized opened file and bounded asynchronous response chunks. Derive size from that opened file, retain range semantics, handle empty and unsatisfiable ranges without underflow, and let response cancellation release the file. Avoid source-sized allocations and unchecked integer conversions.

Use 64-KiB response chunks and a length-limited reader. Invalid or unsatisfiable single ranges return 416 with the opened file's `Content-Range: bytes */size`; reject multipart ranges and zero suffixes. The empty full representation is a valid zero-length 200 response. Both outcomes retain authorization and private/no-store response caching. [HTTP semantics, range requests](https://datatracker.ietf.org/doc/html/rfc9110#section-14)

Copy seek requires truthful timestamp mapping. A bounded pinned-tool measurement found that input seek at five seconds retained source frame 96 at the four-second keyframe, while AAC encoding started near five seconds. Assigning a five-second origin to that output mislabels video and offsets audio by almost a second. Preserve timestamps for the negotiated copy profile, inspect the owned stable initialization/first-fragment timing within startup bounds, and return the actual normalized HLS origin with the requested position. The client must start at the corresponding local offset before playback, allowing decoder preroll without displaying it as requested content. Independently decode at source time five seconds and retain frame-120 and A/V checks. FFmpeg documents nearest-seek-point retention and the effects of `copyts`, `start_at_zero` and muxer timestamp rewriting in its [official CLI documentation](https://www.ffmpeg.org/ffmpeg.html).

Packet timestamps alone do not establish an MSE timeline. The actual client run found fragment `tfdt` values of zero while MP4 edit lists held four-second video and 4.978-second audio delays; hls.js did not apply those delays. The negotiated profile therefore also fixes the nested MOV options to `use_editlist=0:movflags=+frag_discont:avoid_negative_ts=make_non_negative`. The outer HLS setting does not control the child muxer's timestamp policy. The [pinned FFmpeg 8.1 MOV source](https://www.ffmpeg.org/doxygen/8.1/movenc_8c_source.html) explains the separate edit-list, start-DTS and negative-timestamp behavior. Reject remaining edit-list-dependent output before publication. Measurements cover all five SDR HEVC/AV1 container variants at zero/five seconds and H.264 High with B-frames, AAC copy/encoding, exact source-frame hashes and the selected 880-Hz audio. The common initial non-negative shift is bounded; positive seeks retain the actual video/audio clock relationship. No `negative_cts_offsets` option is introduced.

## Client admission and decoder recovery

Resolve preferences, selected tracks, quality and transport before preparation. Validate the finite descriptor set, then run exact `file` or `media-source` capability queries within one bounded preflight deadline. MSE candidates also require precise MIME support and hls.js baseline support. Preserve independent unavailable/rejected/timed-out outcomes and all three reported flags. Recheck operation, profile and source ownership after every asynchronous boundary; abort prevents stale result adoption.

Select an eligible low-transformation route only when support and smoothness are positive. Power efficiency is informational. Otherwise retain conservative H.264/AAC fallback or the existing explicit HDR refusal. Refresh position and pause intent before any replacement Start; file and track operations must not reuse another source's observation.

Add an explicit decoder downgrade for newly negotiated SDR video-copy HLS, separate from server-observed FFmpeg failure. A genuine current-source native decode error 3 or fatal hls.js media error may request the verified compatible fallback. Revalidate authorization, source, selected tracks, current generation and admitted limits under the existing row lock; require fresh generation-bound fallback support and smoothness. Retire the old worker/cache and start bounded software Encode/Encode at the confirmed position with no intentional source-position skip. Persist/publish the canonical replacement only with the transaction. Preserve logical session, pause intent, tracks and the shared two-replacement budget. Duplicate/stale hints cannot allocate or overwrite canonical state. Existing decoder-skip recovery remains separate.

Native error 3 during MSE/HLS also enters the existing local media retry. A small shared controller coalesces native/hls.js reports, allows one local retry per attachment and bounds unresolved local recovery to five seconds. Retain the pre-reload position, use current pause intent, and dispose timers/listeners before source replacement or Stop. A repeated genuine failure reaches the generation-bound server fallback; the local retry does not spend a server replacement attempt. Code 4 and network/authentication errors do not become decoder hints.

The compatible video validator permits 1,000–10,000,000 bps so genuinely low-bitrate source descriptors can retain their admitted ceiling. The prior 100,000-bps floor excluded most reference sources despite valid codecs. Reserve the selected AAC bitrate from the same total device, network-safety and explicit request budget before allocating video; refuse an infeasible combination. Recheck saved total, source, resolution and channel limits before recovery. This changes no maximum or retry budget; low-rate compatible encoding can reduce quality and uses the existing disclosure.

For negotiated routes, the compatible fallback also uses verified scan-descriptor bitrate ceilings when older container fields are absent. Automatic failed-worker recovery revalidates the authorized healthy source under the same heartbeat transaction before reserving an attempt or stopping/restarting its worker. Legacy recovery remains unchanged. The shared revalidation helper has real revoked-profile and unhealthy-file seek coverage; the new failed-worker call is not a separate runtime proof of source mutation during a stall.

## Next evaluation: structured probe cancellation

Evaluate a small scan-owned task group and a dedicated probe-process service. Cancellation should stop new admissions, signal active probes, await confirmed child exit and stream-reader completion, then release concurrency permits and report scan completion. Cover scheduled scans, filesystem notifications and server shutdown through the same owner. Preserve ordinary probe attempt budgets, the separate five-second aggregate optional-enrichment deadline and original media; there is currently no single scan-wide deadline.

The current `library_scanner.rs::phase3_probe` creates a local two-permit semaphore and retains ordinary spawned handles. Dropping its caller detaches active probes. `probe_process.rs::capture` normally reads bounded stdout/stderr concurrently with child exit, and requests termination plus waiting after timeout or output failure. Its final post-kill wait is outside the execution timer, while external caller cancellation can drop that cleanup path. Scheduler cancellation records completion before joining scan cleanup; filesystem watchers spawn actual scans outside the application's task tracker. Consequently the tracked shutdown drain does not yet establish that every scan/probe has exited before the database pool closes.

Prefer a small `services/media_probe` owner for children, pipe readers, execution deadlines and permits, followed by a `services/library_scans` owner for scan identity, cancellation, completion and status. Keep codec parsing/enrichment in the existing scanner modules. HTTP, scheduler and watcher entry points should become adapters to the same scan owner. First qualify the process owner using real silent, delayed and oversized-output children, cancellation during capture, caller abandonment and shutdown with queued work. Require child exit and reader completion before permit release, and prevent new admissions after shutdown starts. Library-wide cancellation claims must wait until every caller uses the owner. Overlap policy, cancellation-status API and shutdown failure behavior remain decisions for that separate design review.

Tokio's [process documentation](https://docs.rs/tokio/latest/tokio/process/struct.Command.html), discovered and opened through MCP on October 18, explains that process handles can outlive dropped callers and recommends explicit wait/kill for stronger cleanup guarantees. Its [JoinHandle documentation](https://docs.rs/tokio/latest/tokio/task/struct.JoinHandle.html) states that dropping the handle detaches its task. Its [TaskTracker documentation](https://docs.rs/tokio-util/latest/tokio_util/task/struct.TaskTracker.html) separates cancellation signalling from waiting for tracked tasks; waiting requires both a closed tracker and no remaining tasks, and closing alone does not prevent later admissions. These are useful building blocks, not proof of child reaping by themselves.

The advantage is verifiable ownership of probes, permits and scan status during cancellation. The cost is a more explicit lifecycle and careful handling of shutdown deadlines, reader failures and cleanup retries. Prefer this refactor over increasing codec breadth next: the expanded descriptor scanning now makes this lifecycle boundary more valuable. Acceptance should use actual slow, silent and oversized-output child processes, cancelled callers and shutdown races; a timeout or dropped handle alone must not count as confirmed cleanup. A separate design review will settle that increment's shutdown behavior before implementation.
