## Existing contracts and correction

Direct file, HLS manifest, rendition playlist, and segment routes use `AuthenticatedUser`. Its credential sources are the HttpOnly `session` cookie followed by an `Authorization: Bearer` header. Playback-start returns relative stream URLs and distinct playback-session and transcode-session IDs; neither UUID is an authentication credential. There is no stream ticket or query-token contract.

The transcode route parameter identifies the in-memory transcoding session. The owning active `play_sessions` row must therefore be found through `metadata.transcode_session_id`, scoped to the authenticated account and active profile, with `stopped_at IS NULL`. Looking up `play_sessions.id` with that transcode UUID incorrectly rejects valid streams. The focused playback `transcode_access` service owns the corrected binding lookup and then applies the existing profile library/rating checks to the bound media item. Missing, stopped, wrong-account, wrong-profile, and replaced-on-seek bindings fail with the existing session-not-found error. Generic playback-session lookups keep their existing semantics.

Using PostgreSQL's JSON text extraction avoids casting untrusted stored metadata to UUID and treats absent or malformed metadata as a non-match. This requires no schema migration and retains existing metadata compatibility. A dedicated indexed foreign key would make the relationship clearer but expands this correction's scope and is deferred. Source: [PostgreSQL JSON operators](https://www.postgresql.org/docs/current/functions-json.html).

## Browser and bundled desktop transport

Same-origin browser playback can use the server's HttpOnly cookie for direct video and HLS. The cookie has `SameSite=Strict`. A bundled Tauri frontend and its selected server have different origins; neither `video.src` nor native HLS supplies an application-controlled Authorization header. Enabling cross-origin cookies does not turn a bearer token into a cookie or override the cookie's same-site policy. Source: [HTML media resource fetching](https://html.spec.whatwg.org/multipage/media.html), [HTML CORS settings](https://html.spec.whatwg.org/multipage/urls-and-fetching.html#cors-settings-attributes).

The accepted minimum transport uses authenticated hls.js on platforms with supported Media Source Extensions for selected-origin bearer sessions. Playback-start requests HLS through the existing `force_transcode` field when raw direct playback cannot carry credentials. The focused source service adds bearer authorization to every manifest, playlist, initialization, and media-segment request, restricted to the selected server origin. It stops pending loaders when account/profile/server/session scope changes. The native HLS fallback remains available only where cookie authentication is valid; unsupported bearer/MSE playback must present a persistent error. Transcoding policy, capacity, codec, and platform limits remain authoritative. Sources: [hls.js configuration](https://hlsjs.video-dev.org/api-docs/hls.js.hlsconfig), [hls.js loaders](https://github.com/video-dev/hls.js/blob/master/docs/API.md?plain=1).

This design avoids buffering complete media files as browser Blobs and avoids introducing a URL credential. A native Tauri range proxy could preserve direct playback without transcoding, but would require a separate native transport implementation, bounded Range forwarding, lifecycle management, and platform qualification; it is outside this implementation.

## Desktop session bootstrap boundary

The desktop shell already provides normalized saved-server state and OS keyring commands keyed by server origin. The shared web UI previously had no production call to restore that origin/token and its auth store retained only a user summary. The focused desktop session service must restore the selected saved server before the first API/session request, read its keyring token, and configure the existing API origin/bearer hooks. Login persists the returned session token only through the native keyring command; logout/session expiration removes that selected-origin token and clears the in-memory bearer. The browser continues using its existing HttpOnly cookie, and raw credentials must never enter localStorage, saved-server JSON, URLs, diagnostics, or messages.

The existing Tauri invoke boundary supports these registered application commands without adding a new credential API. It is an application-internal boundary, not a remote web origin permission. Sources: [Tauri runtime authority](https://v2.tauri.app/security/runtime-authority/), [Tauri capabilities](https://v2.tauri.app/security/capabilities/).

`initializeDesktopSession()` returns only `{ isDesktop, server, requiresServerSelection, hasToken }`; root startup awaits it before `auth.init()`, API setup checks, or `auth.checkSession()`. `selectDesktopServer({ input, networkMode })` uses the existing native normalization, readiness probe, saved-server, and keyring-read commands. Credential writes and clears are serialized and bound to the expected server origin. `auth.resetForServerSelection()` clears only memory and its operation generation, preserving another selected origin's cached summary and secure credential for a later return.

Desktop cached user summaries are whitelisted and scoped by normalized server origin, and are adopted only after the existing session API accepts the token. That API does not return a fresh `UserSummary`, so cached identity and capabilities are not claimed fresh; API authorization remains authoritative. A missing/invalid summary requires actual login rather than inventing an account. If caching a newly authenticated user fails, the just-written native token is cleared and the error remains visible. Session 401 removes the selected-origin secure credential; network failure retains it for retry. No current-user endpoint is introduced in this change.

The focused native session and shared auth services are implemented and unit-tested. Desktop transport/native qualification remains pending. Pure service tests and browser mocks cannot prove OS keyring or native WebView behavior; that claim requires the actual shared Tauri journey.

## HLS file and public URL binding

FFmpeg 8.1.2 in the existing `duskcue:local` image was run against the real cached H.264/AAC clip to inspect both single-rendition and master/media fMP4 output. The single output consists of `manifest.m3u8`, `init.mp4`, and `seg_0000.m4s` onward. Its `EXT-X-MAP` points to `init.mp4`, and media URI lines contain bare segment filenames. The master output points to `720p/index.m3u8`, with the same initialization and segment naming inside that directory. Those raw relative paths cannot be served directly under the current public manifest route because public segment routes require a rendition component.

The focused playback `hls` service preserves the physical output and rewrites public URI references to `/api/v1/transcode/{transcode_session_id}/{rendition}/...`. A single rendition uses the actual session rendition name; master references must identify a validated existing variant playlist, and its parent directory defines the physical initialization/segment directory. Flat legacy `{rendition}_index.m3u8` variants remain compatible. Both `manifest.m3u8` and `{rendition}/index.m3u8` media responses normalize map and segment URLs. No arbitrary rendition fallback, duplicate rendition alias, or traversal/absolute/external playlist URI is accepted.

The FFmpeg boundary explicitly sets `hls_fmp4_init_filename=init.mp4`. Allowed output files are that initialization file and decimal `seg_*.m4s` media files; initialization uses `video/mp4`, media uses `video/iso.segment`. Generated master bandwidth values remain in bits per second. Unsupported URI-bearing tags, including encrypted keys, separate audio renditions, and I-frame playlists, are rejected because the current transcoder does not produce or serve those resources. These are output-contract constraints, not a general-purpose HLS proxy. Sources reviewed 2026-10-07: [FFmpeg HLS muxer options](https://www.ffmpeg.org/ffmpeg-formats.html), [FFmpeg HLS initialization option](https://www.ffmpeg.org/doxygen/8.1/hlsenc_8c_source.html).

Authenticated account/profile binding and current library/rating checks execute before HLS file serving. URI normalization adds no credential to a URL. The corrected binding/paths still require browser decoding and native/platform qualification; inspecting and serving real FFmpeg outputs alone does not establish native playback or accessibility conformance.

Initialization and media responses use `Cache-Control: private, no-store`. The previous hour-long freshness allowed a cached response to bypass a new account/profile/library decision at the server. Manifest and media-playlist responses already prohibit storage. This makes subsequent requests recheck the active binding and access policy; it does not revoke media bytes already held by an active decoder. Source reviewed 2026-10-07: [HTTP Caching, RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2.5).

## Selected-origin real-time events, 2026-10-07

The existing events facade used a fixed `/api/v1/events` native `EventSource`, which cannot attach the desktop's bearer header. The focused `lib/events/transport.js` service now uses `buildApiUrl('/events')` and the shared origin-restricted `streamRequestHeaders` boundary. The browser cookie branch retains native `EventSource`; the bearer branch uses Fetch streaming with its own abort controller, reader and reconnect timer. Authorization remains in headers, credentials never enter event URLs or diagnostics, and authenticated redirects are rejected. Captured authorization/origin and source ownership are rechecked before opening, decoding or reconnecting. Closing or replacing a source cancels its reader/request/timer and prevents queued obsolete events from reaching current subscribers.

The separate `lib/events/framing.js` parser follows the current [WHATWG SSE format and interpretation](https://html.spec.whatwg.org/multipage/server-sent-events.html#server-sent-events), reviewed 2026-10-07: incremental UTF-8 decoding, one leading BOM, CR/LF/CRLF boundaries, comments, literal field names, joined data lines, default/named events, inherited/empty event IDs, ignored NUL IDs, and decimal retry fields. Events require a terminating blank line; incomplete EOF frames are discarded. Reconnection sends the committed ID in `Last-Event-ID`, with UTF-8 header bytes. The actual server supplies named JSON events, UUID IDs, `retry: 5000`, 15-second comment keep-alives and a per-user replay ring; this change preserves that server contract.

The adapter applies explicit product bounds: 1,048,576 UTF-16 code units per frame, 16 KiB decoding slices, one reconnect timer, and a retry delay clamped to 250 ms–60 seconds. Overflow and invalid content type close the stream. HTTP 401/403/204 and other terminal client failures stop reconnection; transient network/408/429/server failures retry while scope remains current. These limits supplement the protocol and are not claimed as requirements imposed by WHATWG or WCAG. The facade detaches a type when its final subscriber leaves, reattaches it correctly after a later subscription, and rejects stale dispatchers/open callbacks after reconnect.

Focused unit evidence uses actual `ReadableStream` chunks and `Response` objects for UTF-8 boundaries, framing, Last-Event-ID/retry, cancellation, scope changes, foreign response rejection, HTTP failures and bounded buffering, plus facade listener/reconnection tests. The final `node scripts/testing-memory/run.mjs web-unit tests/unit/events-transport.test.ts tests/unit/events-store.test.ts` run passed 21 tests in 727 ms; memory evidence is ignored `.cache/testing-memory/2026-10-07T13-55-34-504Z-e05c6992-8255-45ba-ab9e-3b132df65a73.jsonl`. The focused JavaScript and TypeScript test check with the repository's non-strict settings passed, as did `git diff --check`. These tests establish transport/service behavior; real Tauri event delivery and server replay remain separate integration evidence. The events endpoint remains account-scoped as implemented by the existing server; no server authorization rule or profile event taxonomy was changed.
