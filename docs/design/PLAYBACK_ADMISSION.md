## Confirmed product decisions

1. Build and qualify the shared household/optional Live TV reservation foundation first: atomic admission, renewal, revocation and confirmed release. Production enforcement, VOD delivery/client migration and Live TV play actions remain disabled/separate until those paths and worker shutdown are integrated.
2. Each independent playback session counts once, including preparation and pauses, regardless of direct play, transcoding or shared upstream channels. Parallel media reads and seek/source recovery within that logical session do not create extra viewers. Encoder capacity remains a separate physical resource limit.


3. Preserve valid user override → assigned/default-policy inheritance and current defaults. Zero denies new viewers; a resolved null ceiling is unlimited. Negative, missing or ambiguous policy data refuses admission until corrected.
4. Renew within sixty seconds, including while paused. Expiry prevents further use and requests retirement; capacity remains counted until owned-resource cleanup is confirmed. Failed or uncertain cleanup never frees a slot by timeout alone.
5. Reservations from an uncertain former owner remain counted until explicit server-operator reconciliation after fencing and physical cleanup. No automatic replay, adoption or timeout-only reclamation.
6. Count server-served online viewing. Download jobs and downloaded offline playback remain outside this ledger and retain their separate existing access rules.
7. One stable start-request identity binds the exact actor/session/profile and intended resource. Matching replay can reconcile existing state but cannot allocate another viewer, extend expiry or revive a terminal reservation. Mismatched reuse is refused.
8. A cap-only reduction blocks new starts while authorized existing viewers can renew. Actual viewing/session/profile/credential/capability/source revocation retires affected reservations; an edit that also advances Live TV source generation retains that revocation effect.
9. A routine metadata refresh can preserve a Live TV reservation when the same private Dispatcharr channel key remains authenticated in the current snapshot, with unchanged assignment/source generation and current viewing permission. Removal or authority change retires it. No public stable channel ID, stream-secret access or network permission follows.
10. Uncertain-owner recovery has two explicit local operator steps: permanently fence the exact old instance, then acknowledge that exact fence revision only after verifying the old processes and output resources are gone. Viewing/household-management APIs have no cleanup-confirmation override.

## Confirmed implementation contract

### Scope and module ownership

Build focused internal `services/playback_admission` modules for types/errors, strict policy, current authority, database operations, reservation/replay, renewal, retirement, supervised ownership and operator recovery. This is an internal service rather than a new HTTP domain; do not create empty handlers or a broad singleton. Its normal-build core and local operator commands are available for later integration, but existing production playback start/heartbeat/stop/direct/HLS routes and client payloads remain unchanged. No production caller attaches an admission owner yet. Controlled qualification attaches one explicitly; it cannot be enabled by a generic JSON setting or undocumented public route.

Keep the shared household cap and optional stricter Live TV cap separate from physical encoder capacity. Existing transcode/bandwidth/delivery policies are not newly enforced by this reservation slice. Preserve their current production behavior and document that the later VOD adapter must enforce its complete decision policy before output. Kids Live TV stays disabled; existing legitimate on-demand Kids/profile restrictions remain authoritative.

Reuse locked Rust/Cargo 1.99.1, SQLx 0.9/PostgreSQL 18, Tokio/Tokio-util and existing auth/profile/encryption/catalog helpers. Add no dependency or new secret store. Reuse the approved standard legal headers only, with no explanatory source comments.

### Durable identity and claims

Add dedicated instance and reservation tables rather than changing partitioned play history. Instance, request/reservation and other new application identities are UUIDv7. A caller creates one request identity before dispatch; it is also the reservation identity, never a bearer credential. Record a bounded immutable fingerprint of the original intended subject and exact account, real auth-session, selected-profile/context revision, credential revision and credential transport. Resource descriptors contain bounded typed identifiers, not URLs, tokens, provider text or arbitrary metadata.

Each instance registers a fresh immutable identity and never silently adopts another instance's reservations. Instance state/revision permanently fences old callers. Reservation states distinguish held, retiring and released; foreign/unowned/expired uncertainty is explicit. Every non-released reservation counts, including preparation, pause, retirement and uncertain cleanup. Expired rows are not omitted from capacity counts. Released receipts remain durable to prevent request revival; there is no automated receipt pruning or history UI in this foundation. A bounded production-retention design is a prerequisite before enabling real admission traffic.

Serialize a short claim on the authoritative household row, with current instance/policy/session/profile/source checks and deterministic lock ordering. Count all owning instances' non-released reservations in the same transaction before insertion; Live TV also counts its sublimit. Zero denies new admission; the user override and selected/default streaming policy are resolved strictly from current database data. Require one valid selected/default policy, valid nonnegative numeric limits and unambiguous typed values. Do not change seeded defaults, rewrite existing user policy or make a missing policy permissive. A resolved null viewer ceiling has no policy ceiling while separate finite service/resource budgets still apply.

An exact replay reconciles the same durable identity and original fingerprint without allocating work again or extending its deadline. Return current state, not an unconditional usable grant. Different actor/profile/resource reuse is refused. No transaction retry may invent a new request identity. A lost commit acknowledgment is indeterminate until that exact claim can be reconciled; media work must not start on assumed success. Retain the command/instance ownership necessary to finish or classify the operation even if an observing caller disappears.

### Authority and verified subjects

Use current active household, owned selected profile, real nonexpired cookie/bearer session, credential/profile-context revisions and resolved capabilities. A legacy synthetic session is not an authenticated reservation context. Fresh household-owner proof remains a management requirement and is not required for ordinary viewing claims. Cleanup remains possible through the captured owner after viewing authority or the selected profile is revoked; it cannot renew or start media.

For on-demand subjects, bind the exact media file/item relation and recheck current library/profile/content access with existing connection-scoped helpers. For Live TV, require a standard selected profile, current `can_use_live_tv`, enabled assignment, explicit profile access, approved matching-generation feed authority and an authenticated current snapshot/channel row. Reuse bounded metadata projection and add only a narrow private-key lookup needed for continuity. Admission derives the private channel key from the authenticated current entry; renewal uses the current verified snapshot and that key. Do not expose the key as a public channel/favorites identifier, decrypt stream/logo fields or fetch imported references.

A fresh claim validates its requested snapshot/entry. Matching request replay retains its original input fingerprint while checking the saved private identity against current authority. A normal metadata refresh may change snapshot-entry UUIDs without creating a new viewer if the verified private channel key and source generation remain valid. Profile/source/channel removal or unreadable/tampered evidence retires affected reservations. A reservation only accounts for a viewer: it is not permission to serve a file, open a network source or attach a different resource.

### Renewal, revocation and owned retirement

Use a sixty-second renewable deadline based on the database clock, with conservative local cancellation timing. Renewal must arrive before expiry, match the exact owner and captured actor/resource context, and validate current authority. Only explicit successful renewal extends the deadline. Reconciliation, status reads and duplicate starts never do. Existing authorized viewers may renew after a cap-only reduction; they still count against new admission. Actual authority/fencing changes and expiry prevent further use and request retirement.

A synchronized per-owner registry closes admission and registers tracked commands/resources together, independently of TaskTracker's closed flag. Own accepted work until it settles; no queue of playback starts and no detached cleanup after observer loss. Keep physical resource ownership until its registered completion/cleanup future has actually finished. An encoder exiting by itself is not proof that a logical viewer's cached output/readers are gone. Later VOD adapters must cover that whole lifetime.

Use finite initial engineering budgets: eight concurrent nonqueued database commands and at most 128 locally owned reservation/resource entries. Public policy-null does not promise unlimited machine resources. Bound subject/fingerprint data to 2 KiB, database operations to three seconds with 500-ms lock / 1,500-ms statement / three-second transaction limits, and controlled cleanup observation to ten seconds. Monitor expiry and revocation with a tracked one-second loop and bounded work; successful renewal/use always rechecks authority rather than trusting a polling cache. These are qualification budgets, not a claim of zero-latency remote revocation or a production sizing promise.

Physical cleanup confirmation is a trusted internal owner completion, never an arbitrary client boolean. Mark released only after completion and a definite durable transition. Keep failed/indeterminate cleanup or release counted until reconciliation resolves it. Cooperative cancellation, task exit/destructors, file/TCP readers and controlled subprocess disappearance receive independent proof. Preserve the existing replayable VOD Stop/history contract by leaving its integration for the next milestone.

### SQL ownership and root shutdown

Reuse explicit bounded connection ownership with default discard on interrupted/unacknowledged transactions, acknowledged rollback/close and no detached connection that can exceed the pool bound. Classify uncertain claim/renewal/retirement commits separately from definitive refusals. Reconcile by the same instance/reservation/fingerprint; do not report success from a timeout or an absent observer. Fail closed if current policy or authority cannot be read.

Add an optional admission owner to AppState/root lifecycle. No normal playback caller registers one in this increment. When attached for qualification, root shutdown closes its admission, signals its resources and awaits command/monitor/resource cleanup before closing database dependencies. Preserve the existing shared thirty-second drain and sixty-second pool-close budgets and nonzero failure/second-signal behavior. Do not lengthen deadlines or claim VOD TranscodeManager has acquired this lifecycle automatically.

### Local operator recovery

Add separate local commands to fence an exact instance at its expected revision and reconcile an already-fenced instance at that exact fence revision with an explicit resources-gone acknowledgment. They use the existing server-local configuration/database authority, a small owned pool, bounded writes and metadata-only audit/output. They do not use household proof or expose an HTTP cleanup override. Missing acknowledgment, stale revision, active/unfenced identity or a foreign reservation cannot release capacity.

Database fencing is an authority control, not physical shutdown evidence. The operator must independently stop/fence the old execution context and verify its processes/readers/output resources are gone before acknowledgment. A fence never reopens an old instance, and reconciliation never replays a start. Tests exercise the actual commands against the disposable database and real controlled resource completion. No operator command will target the user's normal database during qualification.

Use genuine production internal services and disposable PostgreSQL18 for simultaneous mixed on-demand/Live TV claims, household isolation, both ceilings, zero/null/override/invalid policies, replay/mismatched reuse, no revival, unchanged deadlines, preparation/pause counting, cap-only reduction and explicit revocation. Cover profile round trips, credential/capability changes, snapshot continuity/removal, authenticated manifest/row failures, source generation changes, instance fencing and stale operator acknowledgments. No fabricated movie history or delivery authorization is created.

Exercise actual BEGIN/COMMIT acknowledgment loss, caller cancellation and retained command ownership; uncertain outcomes must never silently over-admit or reuse a slot. Use controlled real subprocess/TCP/file resources to prove retirement remains counted through cleanup and error cases, with admission/closure races and optional-owner root drain before pool closure. Run existing owner/assignment/catalog/refresh/root and appropriate playback regressions serially under unchanged resource guards, worker counts and container/pool limits. Add no production bypass route, test trust root or network-permission escape hatch.

The operator-provided private feed values and probe results remain only in ignored local fixtures. It must fetch only the two approved feed resources, with no redirects, ambient proxy, stream/logo fetch or imported playlist traversal. ## Implementation notes

The internal service is split into authority, strict policy, transaction ownership, ledger, typed identity/error, owner command/lifecycle and local operator modules. The optional owner must be attached during bootstrap before request admission. Normal server playback startup leaves its AppState slot empty. An attached owner resolves the current runtime session-idle policy on each authority check; standalone controlled owners receive an explicit fixed idle policy.

A resource factory runs only after a definitely acknowledged fresh claim. It is never called for matching replay, foreign ownership, an indeterminate claim or a refused start. Its trusted completion must cover every child, reader and output resource it owns; a client cannot supply a release acknowledgment. `owned_here` distinguishes a receipt belonging to another instance. A concurrent duplicate while the original command is pending returns `Pending` without queueing another claim or competing resource factory. Reconciliation of a locally retained uncertain command cannot insert an absent reservation. Terminal database receipts prevent revival after the local entry is gone.

Household row locks serialize the count and insertion. A compatible short SHARE table lock also stabilizes streaming-policy defaults against concurrent insertion/deletion or default changes; it lives only inside the bounded transaction and introduces brief policy-write contention. This favors explicit strict policy evidence over a permissive missing/default fallback. Existing production policy behavior and seeds remain untouched.

Every transaction starts at Read Committed with explicit local timeouts. Acquired SQLx leases default to close/discard, including an executed but unacknowledged BEGIN; no connection is detached beyond its pool bound. Acknowledged commits produce definite results. Lost claim/renewal/release commit acknowledgment remains indeterminate to that observer. A later exact durable row read can reconcile an already-completed release; a timeout never manufactures physical completion. Local cleanup/release failure remains sticky for root shutdown and blocks further starts on that owner.

Transactional retirement hooks preserve account/session/profile/capability, library/content, Live TV access/source and published channel-removal events. Revoking and restoring a permission between monitor ticks does not revive that reservation. Typed generated actor/subject columns and partial indexes support targeted retirement without cascading receipts. Household serialization and shared file/item/library locks fence in-flight claims against those mutations. Numeric cap-only edits are excluded; viewing-scope edits conservatively require a new reservation. These short locks can produce bounded refusals under conflicting writes. The monitor has rotating bounded priority, while each resource independently tracks its conservative renewable local deadline. Cleanup after account/session/profile revocation uses the captured immutable request and owner, without requiring the vanished viewing authority. The retained reservation has no cascading account/profile foreign key that could silently erase an uncertain viewer. Local operator commands use a one-connection pool, bounded connection establishment/transactions/closure and metadata-only event records.
