## Source findings

- The owner backend already supports status, existing-password proof, passkey unlock, handoff-authorized designation of an existing key, handoff-authorized new registration, and explicit lock. Proof rotates the external credential while retaining the internal session UUID, selected scope and viewing expiry. The grant ends at the earlier of five minutes or viewing-session expiry.
- Initial activation and recovery use an operator-issued, account-bound, one-use ten-minute handoff. No HTTP operation issues it. Recovery issuance revokes old owner trust/grants/challenges immediately. The client must not invent an operator role, substitute a viewing code, or create a password-setting/reset workflow.
- Owner status reports protection, grant expiry, trusted-password availability and trusted-key count. Password availability describes an already designated password; it does not reveal whether an unenrolled account has a password. Ordinary passkey listing exposes IDs/names, without owner-trust flags. New enrollment is bounded to sixty-four keys by the backend.
- Owner proof responses contain expiry and an optional bearer replacement, but no user summary. Existing private login adoption treats an absent user as signed-out. Same-account credential replacement also does not advance the existing frontend auth revision. Neither behavior is suitable unchanged for owner proof.
- The bounded API mode currently replaces problem titles with `HTTP_<status>`. `OWNER_002` is a bad/expired proof or handoff, not necessarily expired viewing authentication. `OWNER_003` covers both lockout and temporary capacity, with no lock-until or Retry-After. Do not infer a fifteen-minute countdown from that response.
- `/user/sessions` lists all account sessions without identifying the current one or its account/generation. `/profiles` identifies current profile, but not exact account/session/generation. Owner status likewise lacks identity. Existing session revalidation restores cached user data after probing session validity; that cannot establish an exact authoritative session context.
- The auth store has revision/origin guards; native session persistence serializes secure-store operations and writes the keyring before publishing the bearer. There is no owner-specific rotated-session adopter, metadata-only auth-change synchronization or authoritative cookie-context reconciliation.
- The packaged Windows application actually runs at `http://tauri.localhost/` in the prior native evidence. Selecting a server changes API origin and bearer, not document origin. The verifier has one configured RP ID/origin, normally the hosted server. No native WebAuthn bridge or origin mapping exists. This is an origin mismatch, not proof that the platform exposes no credential API.
- Ordinary passkey login expects the wrong start-response wrapper and has no qualified JSON option adapter. A focused owner ceremony adapter is needed. General ordinary-login repair remains a distinct task; do not silently claim it is qualified by owner tests.
- Live TV management additionally needs retained body-plus-ETag handling and independent admin/owner authority. Its self-household administrator saves revoke the proof used for that save, and saved URLs/origins/addresses are never read back. This is another reason to qualify owner/session handling first.

Concrete source boundaries: `server/src/domains/household_security/`; `server/src/domains/auth/{types,handlers,service}.rs`; `server/src/extractors.rs`; `clients/web/src/lib/stores/auth.js`; `lib/desktop/session.js`; `lib/api/core.js`; `routes/+layout.svelte`; and the existing browser/native qualification harnesses. ## Alternatives, pros and cons

| Approach | Pros | Cons | Decision |
|---|---|---|---|
| Owner-security UI before all Live TV forms | Qualifies credential adoption once; keeps proof/recovery reviewable. | Assignment/network/refresh controls still need their next UI increment. | Confirmed. |
| Build every management form now | Broad initial functionality. | Couples secret forms, ETags, revocation and asynchronous imports to an unqualified client auth transition. | Deferred. |
| Dedicated household settings screen | Clear distinction from server administration; accessible, reusable destination. | Related forms initially navigate to it rather than automatically continuing mutations. | Confirmed. |
| Browser passkeys plus native existing-password proof | Reuses the actual server RP and native keyring; no trust expansion. | Passkey-only households use the hosted browser for management. | Confirmed. |
| Expand trusted origins or transfer a browser grant to desktop | Could appear to simplify a unified interface. | Changes the established origin/session trust model and needs its own protocol/qualification. | Excluded. |
| Authoritative session context plus guarded adoption | Can detect account/session/profile/generation changes and reconcile cookies without cached identity assumptions. | Small backend read/DTO/binding addition and adversarial concurrency tests. | Confirmed. |
| Interpret any proof 401 as logout, or automatically repeat a timed-out proof | Less recovery state. | Bad proof does not mean expired viewing; a committed rotation cannot safely be replayed. | Reject. |

## Confirmed implementation contract

### Session context and binding

Add authenticated `GET /api/v1/auth/session-context` with no-store on success and outer failures. Return only current account/session/profile IDs, profile-selection state, cookie/bearer/legacy transport, existing session expiry, observation time and opaque decimal-string credential/profile-context revisions. Include a versioned, nonsecret context identifier derived from the stable identity/revisions. It is not proof, an access token or a grant. Support ordinary authenticated startup/profile-selection contexts; owner operations still require a selected standard profile.

Read current database state consistently and reject revoked/mismatched generations instead of trusting the extractor's older snapshot. Reuse cancellation-safe, bounded request/database ownership; add no detached read task or new shutdown budget. Owner status and successful proof also identify their actual server context. The client can then verify metadata together rather than combining identity and grant evidence from unrelated sessions.

The owner client sends a bounded `X-Session-Context` binding on owner status/password/passkey/lock requests. A supplied binding is checked against the live transaction scope before consuming a challenge/handoff, incrementing a proof-failure counter or writing a grant. Malformed and stale bindings receive fixed refusals. Existing callers without this new binding retain established backend permissions and proof requirements. The binding never substitutes for those requirements. General authenticated session validation should use the new authoritative read rather than an all-sessions validity probe plus cached identity alone.

### Screen and trusted-factor flows

Use `/settings/household`, discoverable for selected standard profiles. Direct Kids entry exposes no owner controls or owner requests. Keep the server-superuser role separate from the household owner designation. Show server-reported protection, available trusted-factor kinds and the current bounded management grant, with explicit Check status and Lock actions. Expiry disables management presentation without signing out ordinary viewing; no sliding renewal, polling proof or automatic mutation continuation.

Support normal unlock through a trusted existing password or browser passkey. Provide an explicit operator-handoff enrollment/recovery section for fresh proof of an existing password, designation of one listed existing account passkey, or registration of a new browser passkey. Explain activation and the related protected profile/passkey mutations before the explicit final action. The client does not issue handoffs, create a password, reset ordinary login credentials or provide another management PIN.

Use one pasteable handoff field and password-manager-compatible labeled inputs. Never trim password bytes. Apply backend UTF-8/name/key-count bounds and display fixed validation messages. Keep passwords, handoffs, challenges and credential material out of application storage, URLs, logs, notifications and broadcasts. Clear sensitive inputs on submit, cancellation, expiry and scope exit. User-agent password-manager behavior remains available. Passkey names/variants are text, never HTML.

Browser ceremonies run only in the hosted secure/locally trustworthy context with a usable credential API, explicit JSON conversion and server-provided RP/challenge settings. Never rewrite an RP ID, relax origin verification or infer successful authentication from capability detection. Tauri offers password proof where an existing password is usable and clear hosted-browser guidance for passkey work; no native passkey grant transfer or bridge is added.

### Proof ownership and recovery

Use a focused auth-owned credential-adoption coordinator rather than feeding a proof response into login adoption. Capture current frontend revision, server, account, exact session and profile context before submission. Advance credential/auth generations so an older authentication probe cannot clear a newer result. Publish no management success until the replacement transport is usable and a current server context/status confirms it.

A proof/lock submission can commit before a response arrives. Retain submitted credential-replacement work through response handling and native persistence even if its screen is disposed; discard screen callbacks and secret fields separately. Deliberate server/account/logout transitions supersede adoption and must not overwrite or clear newer credentials. Profile changes revoke grants; they must not revive an earlier profile's management state. Never restore an old server token as rollback.

For native bearer proof, persist only into the captured origin's secure store before publishing the new bearer; preserve the account/viewing summary. Native write completion remains owned until acknowledged, including after a UI deadline. Retain/quarantine the credential operation rather than accepting another unsafe replacement while an older write can still complete. A persistence failure or missing replacement stays fail-closed and offers explicit sign-in recovery without touching a newer context.

For cookies, JavaScript cannot undo a Set-Cookie already applied by the browser. Verify the actual server context, coordinate metadata-only session-change invalidation across same-origin tabs and clear stale protected presentation. A notification grants no authority. If actual account/session no longer matches, require explicit reconciliation/sign-in and do not revoke a newer server session as cleanup. A lost/malformed response offers a safe status/context check where possible; no automatic proof replay. Preserve the existing behavior for unrelated API callers.

Bad owner proof (`OWNER_002`) shows a fixed owner error without logging out viewing. Only independently confirmed current-session expiry uses the established sign-in recovery. Preserve an allowlist of owner/auth error codes in bounded parsing without exposing arbitrary server details. Treat lockout/capacity as unspecified until server evidence supplies Retry-After; do not invent a lockout expiry. Every stale response, cancellation or failed verification clears management authority in the UI.

### Bounds, accessibility and qualification

Use at most one credential replacement per client auth owner, no queue of proofs, and bounded concurrent metadata reads. Owner JSON success/error materialization is capped at 256 KiB; request material follows the existing 64 KiB backend bound and strict DTO projection. Use fifteen-second HTTP/UI operation deadlines and a bounded browser ceremony within the backend's two-minute challenge lifetime. Timeouts do not establish rollback or native-write completion. Respect valid Retry-After before explicit retry; never resubmit automatically.

Display localized dates/device-zone information and fixed status messages with actual fallback language. Preserve exact server expiry/revision strings; use conservative elapsed-time accounting and revalidation for UI expiry rather than extending authority from a browser clock. Provide native controls, persistent programmatic status, accessible errors, keyboard/focus restoration, 320 CSS pixel reflow, zoom/RTL and contrast qualification. Do not announce a changing countdown every second.

Test real production backend routes with disposable PostgreSQL for current-context identity, stale binding, generations, profile round trips, no-store, cookie/bearer rotation and grant/recovery invariants. Test actual browser WebAuthn registration/assertion with a virtual authenticator and real server verification at the configured RP origin; fixture-only callbacks do not qualify that ceremony. Exercise response loss, delayed Set-Cookie, concurrent tabs/login/logout/profile/server changes, bad-proof versus expired-session handling, secure-store failure/late completion and no secret leakage. Reuse real isolated Tauri password/keyring/transport/accessibility qualification. Record hardware/screen-reader/OS limitations honestly and run heavy checks serially under unchanged resource guards.

Keep Live TV configuration/delegation/destination/refresh forms, scheduling, client playback, Kids policy, native passkeys, ordinary passkey-login repair and independent recovery notifications separate. Reuse locked dependencies and the existing legal-header exception. The confirmed workflow is modular implementation, qualification and documentation followed by commit/push on main without release or PR merge.

## Session-context response

| Field | Wire contract |
|---|---|
| `user_id`, `session_id`, `profile_id` | Current database UUID strings; new persisted application IDs retain UUIDv7. |
| `credential_revision`, `profile_context_revision` | Opaque nonnegative decimal strings, never JavaScript numbers. |
| `profile_selection_required` | Current boolean; owner operations still require a selected standard profile. |
| `transport` | `cookie`, `bearer` or `legacy`; owner proof does not elevate legacy access. |
| `session_expires_at`, `observed_at` | Exact UTC instants; the client accounts conservatively for elapsed request time. |
| `context_id` | `sc1.` plus 43 base64url characters, a nonsecret digest of stable identity/revisions/selection. |

Owner status and successful proof add `context` with this projection. Cookie proof returns no body token; bearer proof returns its replacement `session_token`. The UI displays locked when evidence has already expired in transit. Metadata notices carry only origin and a random deduplication nonce. The default-close SQLx read trades connection reuse for explicit cancellation ownership; this low-frequency surface adds no polling or extra pool.

## Implemented outcome

The shared screen is available at Settings → Household management for selected standard profiles. It supports operator-handoff enrollment/recovery, trusted password/browser passkey proof, absolute grant status and explicit lock. Native password proof uses the captured server origin's keyring; passkey-only households use the hosted browser. Secrets stay in memory and clear on submission, expiry, failure and teardown. Native fields permit password managers/paste; semantic status, focus restoration, fallback-language annotations and device-zone expiry preserve the existing shell.

The focused `household` client services own DTO projection, WebAuthn JSON conversion, screen cancellation, session-change notices and retained credential replacement. Generic exact-time formatting is shared under `lib/time`, preserving the existing catalog exports. Proof responses do not enter ordinary login adoption. The auth owner retains submitted work through native completion, guards its original revision/server/account and confirms actual context before publication. Queued native cleanup rechecks authority before touching secure storage. A known bad owner proof leaves viewing signed in; a separate current-session revalidation handles actual expiry. Failed reads discard protected presentation and require an explicit recovery action.

`GET /api/v1/auth/session-context` is authenticated and no-store, including outer failures. It returns only current identity, selected profile, transport, expiry, observation and decimal revisions. The `sc1.` SHA-256 digest is a nonsecret contextual binding, not a credential. Its database read has a ten-second bound and a default-close lease; no unowned read task or new shutdown budget is introduced. Owner status/proof return context. An optional exact-length `X-Session-Context` is transaction-checked under current scope locks before proof side effects; malformed bindings return `OWNER_005`/400 and changed bindings `OWNER_007`/409. Existing unbound callers retain the original proof rules. No migration, dependency version or UUID strategy changes.

The recommended stack remains the existing Rust 1.99.1/Axum/SQLx/PostgreSQL verifier, Svelte shared settings screen, native WebAuthn JSON APIs with bounded compatibility conversion, and Tauri's origin-keyed OS credential store. Main only; no release, PR merge, deployment or changelog change.
