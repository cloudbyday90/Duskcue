# Internationalization (i18n)

## Overview

This document is the authoritative design for internationalization (i18n) and localization (l10n) across Duskcue — the strategy by which the server, web client, and future desktop/mobile clients adapt to the user's preferred language, locale, and text direction. The goal is to make Duskcue usable for non-English speakers without blocking v1.0 on translation completeness.

The decision documented here: **i18n-ready at v1.0, English source language, community-driven translations post-launch.** Adopt Paraglide JS for the web client, Fluent for server-side templates, ICU4X for formatting. Translations accepted starting v1.0 via Weblate; English-only is the v1.0 ship language.

## Scope

**Covers:**

- Translation library choices for each client tier (web, server, future mobile/desktop)
- Source language and fallback chain
- Translation file format and storage
- Locale negotiation (Accept-Language, user preference, URL prefix)
- Right-to-left (RTL) language support
- Plural rules, gender, and other CLDR concerns
- Translation contribution workflow (Weblate)
- What gets localized vs. what stays English-only
- Phase 13 notification template localization pattern

**Does NOT cover:**

- Media metadata language selection — already configurable via `metadata_language` (TMDb returns localized metadata per language)
- Subtitle language selection — already user-configurable via subtitle preferences
- Date/time storage — timestamps are always UTC ISO 8601 in DB/API; formatting is locale-aware only at display time
- API field names — protocol layer is always English (programmatic identifiers)

## Decision — i18n-Ready at v1.0

**Duskcue commits to i18n infrastructure at v1.0 but ships English-only translations. Community translations unlock non-English locales as they reach translation-completeness thresholds.**

### Why i18n-Ready (Not i18n-Deferred)

Three factors make "build it now" cheaper than "retrofit later":

1. **Phase 13 notification templates land soon** — The `notification_types` table already has an `in_app_template` column with English strings seeded in Phase 2. If Phase 13 ships template rendering without an i18n abstraction, every template gets baked in as English. Retrofitting requires migrating the DB schema, rewriting the template renderer, and re-translating every notification — costly rework for marginal new functionality.

2. **Web client UI surface is still small** — Phase 8 has ~24 route pages, each with a handful of user-facing strings. Wrapping strings in Paraglide now costs minutes per string; wrapping them after 5 more phases of UI work costs days. The "extract string" operation is a one-keypress IDE action with the Sherlock VS Code extension.

3. **Compiler-based i18n has zero runtime cost for English-only** — Paraglide JS compiles translations to tree-shakable JavaScript functions. For a deployment with only English translations loaded, the bundle size is identical to a hardcoded-English app. There is no "i18n tax" on English-only deployments.

### Why English Source (Not Multilingual From Day One)

- **English is the development language.** All code, code comments, commit messages, error messages, and developer docs are English. Source-language translations match the developers' mental model.
- **Translations lag development.** Every UI change requires updating the English source; non-English translations follow when translators get to them. v1.0 will have UI churn as users surface bugs and UX feedback — pre-translating churns translations and frustrates translators.
- **Translation completeness matters.** A partially-translated UI (mixed English/native) is worse than a fully-English UI. Shipping v1.0 English-only avoids the "70% translated" embarrassment.
- **Community translation needs a stable baseline.** Translators do their best work against a stable v1.0 reference, not a moving target.

### Target Locales

Duskcue targets **8 launch-window locales** covering the majority of potential users. English is the source language; the other 7 receive initial AI-assisted translations that ship as "preview" (not UI-activated) until native-speaker review confirms quality. Additional locales unlock as community demand and translator availability warrant.

| Locale | BCP 47 | Speakers | Direction | Notes |
|---|---|---|---|---|
| English | `en` | 1.5B+ | LTR | Source language; all strings authored here |
| French | `fr` | 320M | LTR | Informal register (`tu`); French typography (space before `:` `;` `!` `?`, guillemets « ») |
| German | `de` | 130M | LTR | Informal register (`du`); matches Netflix Germany / Spotify convention |
| Spanish | `es` | 560M | LTR | Informal register (`tú`); neutral Spanish understood across Latin America + Spain |
| Italian | `it` | 85M | LTR | Informal register (`tu`) |
| Arabic | `ar` | 420M | **RTL** | MSA (Modern Standard Arabic); RTL layout review required before activation; masculine-default for verbs where user gender is unknown (standard MSA practice) |
| Chinese (Simplified) | `zh-Hans` | 1.3B | LTR | Mainland China + Singapore; no pluralization; no articles; full-width punctuation (：！？) |
| Chinese (Traditional) | `zh-Hant` | ~50M | LTR | Taiwan + Hong Kong; vocabulary differences from Simplified (登入 vs 登录, 觀看 vs 观看, 偵測 vs 检测) |

**Register decision: informal across all locales.** Consumer media apps (Netflix, Spotify, Apple Music, Disney+) universally use the informal register in French/German/Spanish/Italian. Duskcue is a personal/family media server — the informal register matches the product's tone. This decision is locked at translation-start to avoid rework.

**Translation strategy: AI-assisted initial + native review.** Initial `.ftl` and `.json` translations are generated via AI for the small notification template surface (11 messages) and the web client UI string surface. Each file is marked with a translator comment: `### AI-GENERATED INITIAL TRANSLATION — needs native-speaker review before activation.` Locales are NOT UI-selectable until a native reviewer signs off (per the 90% completeness + review threshold below). Community translators refine via Weblate post-launch.

**Why these 7 and not others.** These 8 locales cover ~4.3 billion speakers across 6 language families (Germanic, Romance, Semitic, Sinitic). Japanese, Korean, Portuguese, Hindi, and Russian are the most likely Phase 2 additions based on media-server user demographics; they are deferred only because translation capacity is finite, not because they lack importance.

## Stack

### Web Client (SvelteKit) — Paraglide JS 2.0

**[`@inlang/paraglide-js`](https://paraglidejs.com/)** is SvelteKit's [officially recommended i18n library](https://svelte.dev/docs/cli/paraglide). Chosen over alternatives:

| Library | Why not |
|---|---|
| `typesafe-i18n` | Maintainer (Ivan Hofer) passed away; project unmaintained |
| `svelte-i18n` | Runtime-based (larger bundles), not type-safe, less active development |
| `@tolgee/svelte` | Tight coupling to Tolgee platform (SaaS); Paraglide is git-native |
| `i18next` + `svelte-i18next` | Runtime-based; less ergonomic for Svelte patterns |

**Paraglide advantages for Duskcue:**

- **Compiler-based** — Translations compile to tree-shakable JS functions; only used messages end up in the bundle. For TV browsers with constrained bandwidth, this matters.
- **Type-safe** — IDE autocomplete on message keys; refactor-friendly.
- **Officially part of SvelteKit** — `svelte.dev/docs/cli/paraglide` is Svelte's own documentation page. Long-term support guarantee.
- **Git-native workflow** — Translations are JSON files in the repo; community translations flow through standard PRs (or via Weblate's git integration).
- **Multiple routing strategies** — URL prefix (`/en/dashboard`, `/de/dashboard`), cookie, baseLocale, etc. Duskcue uses URL prefix for shareability + cookie for sticky preference.

**File format:** Inlang message format (JSON), one file per locale in `clients/web/messages/`:

```json
// clients/web/messages/en.json
{
  "$schema": "https://inlang.com/schema/inlang-message-format",
  "nav_dashboard": "Dashboard",
  "nav_libraries": "Libraries",
  "media_card_rating": "{rating} / 10",
  "items_count": "{count, plural, one {# item} other {# items}}"
}
```

### Server (Rust / Axum) — Fluent

**[Fluent](https://projectfluent.org/)** (Mozilla's localization system, used by Firefox) for server-side templates. Chosen over alternatives:

| Library | Why not |
|---|---|
| `rust-i18n` | Simpler `t!()` macro, but doesn't handle plurals/gender/selectors as cleanly. Translator experience inferior. |
| `gettext` (via `gettext-rs`) | Requires source-code scanning pre-build step; English-string-as-key makes typo fixes painful across translations. |
| `fluent-i18n` | Thread-local locale model (`set_locale()`/`get_locale()`) is unsafe for an async Axum server: tokio tasks migrate between worker threads, so concurrent notification rendering for users with different locales races on the global thread-local. The crate was the original primary choice in this doc; Phase 13b Task 1 research (June 2026) confirmed the API insufficiency this doc anticipated and switched the primary to `fluent-templates`. See "Crate selection rationale" below. |

**Fluent advantages for Duskcue server:**

- **Linguistic expressiveness** — Plural rules, gender, selectors all live in the `.ftl` files, controlled by translators per-locale. Server code stays clean.
- **Translator-friendly** — `.ftl` files are designed for translators, not developers. Comments, terms, attributes all first-class.
- **Mozilla-backed, stable** — Powers all of Firefox's localization; well-tested Rust implementation.
- **Used by rust-lang.org** — Same toolchain, validated in production.

**Crate choice:** [`fluent-templates`](https://crates.io/crates/fluent-templates) — XAMPPRocky's high-level loader built on `fluent-rs`. The `static_loader!` macro compiles `.ftl` files into the binary at build time (single-binary deployment, no runtime file deps — matches Phase 15 Docker goals), and the `Loader` trait exposes `lookup_with_args(&LanguageIdentifier, key, &args)` which takes the locale **explicitly per call**. This per-call locale model is the decisive factor for Duskcue: an async Axum server renders notifications concurrently for users with different locales, so the locale must be a render-time argument, not process-wide or thread-local state. See "Crate selection rationale" below for why `fluent-i18n` was rejected as the original primary choice.

**File format:** Fluent (`.ftl`), one directory per locale in `server/locales/`:

```ftl
# server/locales/en/notifications.ftl

new-media-added =
    { $title } was added to { $library }

library-scan-complete =
    Library scan completed: { $stats }

playback-started =
    { $username } started watching { $title }

## Plural example
new-episodes =
    { $count ->
        [one] One new episode of { $show } is available
       *[other] { $count } new episodes of { $show } are available
    }
```

### Crate Selection Rationale — `fluent-templates` over `fluent-i18n`

This document originally named `fluent-i18n` as the primary crate (with `fluent-templates` as the documented fallback if its API proved insufficient). Phase 13b Task 1 research (June 2026) evaluated both against Duskcue's concurrency model and confirmed the fallback was the correct primary. The decision is recorded here so future maintainers understand why the doc and the code diverged from the original recommendation.

**The decisive factor: locale passing model.** Duskcue's server renders notifications for arbitrary recipient locales concurrently within a single async Axum runtime. Two concurrent requests — one rendering a notification for a German user, another for a French user — must not interfere.

| Crate | Locale model | Concurrency safety in async Axum |
|---|---|---|
| `fluent-i18n` | Thread-local (`set_locale(Some("de"))` then `t!("key")`) | ❌ Unsafe — tokio worker threads run multiple tasks; a `set_locale` in task A before task B's `t!()` completes corrupts B's locale. A per-task lock would serialize all translations globally. |
| `fluent-templates` | Explicit per-call (`LOCALES.lookup_with_args(&langid, "key", &args)`) | ✅ Safe — locale is an argument to each lookup; no shared mutable state. Concurrent renders are independent. |
| `fluent-bundle` (low-level) | Explicit per-call (`bundle.format_pattern(...)`) | ✅ Safe but verbose — reinvents `static_loader!` compile-time embedding and language negotiation. |

**Secondary factors favoring `fluent-templates`:**

- **`static_loader!` macro** compiles all `.ftl` files into the binary at build time via `include_dir`-like expansion. No runtime file I/O, no `CARGO_MANIFEST_DIR` lookup at runtime. Matches Duskcue's single-binary deployment goal (Phase 15 Docker image contains no external locale files).
- **Built-in language negotiation** via `fluent-langneg` (transitive dep) — `StaticLoader` handles `de-AT` → `de` → `en` fallback internally. No custom negotiation code needed for the common case.
- **`Loader` trait** is generic over the loader type, so a future `ArcLoader` (runtime-loaded translations, e.g., for hot-reloading translations from a directory) is a drop-in replacement if Duskcue ever adds operator-editable translations.
- **Mature and maintained** — v0.14 current as of June 2026; powers `rust-lang.org` and numerous Rust web services. MIT/Apache-2.0 dual licensed.

**What `fluent-i18n` would have provided** (now foregone): the `t!("key")` macro ergonomics where locale is implicit. The trade-off is acceptable — Duskcue's server-side translation surface is small (notification templates, not every UI string), and the explicit `lookup_with_args(&langid, ...)` call documents the locale decision at every render site.

**Supporting crates (direct deps alongside `fluent-templates`):**

- `fluent-langneg` 0.13 — `negotiate_languages()` + `accepted_languages::parse()` for Accept-Language header negotiation (used by `services/i18n.rs`).
- `unic-langid` 0.9 — `LanguageIdentifier` type + `langid!` macro for the default-locale constant.

### Number / Date / Duration Formatting — ICU4X

**[`icu`](https://crates.io/crates/icu)** (ICU4X, the Rust port of Unicode's ICU library) for locale-aware formatting:

- File sizes: `1.5 GB` in English, `1,5 Go` in French, `1.5 GB` in German (decimal separator differs)
- Durations: `1h 23m` (English), `1 t 23 min` (French)
- Dates: `June 19, 2026` (en-US), `19 June 2026` (en-GB), `19 juin 2026` (fr), `١٩ يونيو ٢٠٢٦` (ar)

Web client uses the browser's native [`Intl.NumberFormat`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/NumberFormat) and [`Intl.DateTimeFormat`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/DateTimeFormat) — no JS library needed. Server uses ICU4X when formatting strings for notification delivery.

### Flutter Mobile (Phase 16) — Built-in `intl`

Flutter has best-in-class built-in i18n via the [`intl`](https://pub.dev/packages/intl) package and ARB files. Not a Duskcue decision — it's the framework standard. Translation source-of-truth is the Weblate project (see workflow below); ARB files are an export target.

## Locale Negotiation

Locale is resolved in this priority order (highest to lowest):

1. **URL prefix** — `/de/dashboard` → German. Explicit user choice (shareable URL).
2. **User preference cookie** — `duskcue_locale=de` set by language switcher. Sticky across sessions.
3. **Authenticated user preference** — `users.metadata.locale` field, settable via user settings UI.
4. **`Accept-Language` header** — Browser reports user's OS-level language preferences.
5. **Base locale (English)** — Default when no other signal.

**Implementation:** Paraglide's `strategy: ['url', 'cookie', 'baseLocale']` covers URL + cookie + fallback. Server-side handlers read `Accept-Language` for notification rendering when no user preference is set.

**Locale matching:** BCP 47 language tags with region fallback. `de-AT` (Austrian German) → `de` (German) → `en` (English). Uses `unic-langid` crate's `matches()` for negotiation.

## Phase 13 Notification Template Pattern

The `notification_types` table currently stores English template strings in `in_app_template`. The migration path:

### Current (Phase 2 seed, English-only)

```sql
notification_types.in_app_template = '{{title}} was added to {{library}}'
```

Notifications render by simple `{{key}}` substitution in whatever language the template happens to be.

### Migrated (Phase 13, i18n-ready)

```sql
notification_types.in_app_template = 'new-media-added'
```

The column stores a Fluent message ID, not a template string. The notification renderer calls Fluent with the message ID + the notification's metadata as arguments. The actual `services/i18n.rs` implementation uses the `fluent-templates` `Loader` trait (not the low-level `fluent_bundle` API shown in earlier drafts):

```rust
use fluent_templates::Loader;
use unic_langid::LanguageIdentifier;

let rendered = crate::services::i18n::LOCALES.lookup_with_args(
    &locale,                                            // recipient's negotiated LanguageIdentifier
    &notification_type.in_app_template,                 // e.g. "new-media-added"
    &args,                                              // HashMap<String, FluentValue<'_>>
);
```

`services/i18n.rs` exposes thin helpers (`negotiate_locale()`, `render()`) so call sites do not touch the `FluentValue`/`HashMap` construction directly. The `LOCALES` static is produced by `fluent_templates::static_loader!` at module scope and is safe to access from any async context (no thread-local state).

**Migration:** A schema migration converts existing template strings to Fluent message IDs and adds the corresponding entries to `server/locales/en/notifications.ftl`. Future notification types added by Phase 13 dispatch system use the same pattern from day one.

**Per-user locale:** Notification rendering uses the recipient user's `metadata.locale` (falling back through the chain). Different users receiving the same notification type see it in their preferred language.

## Right-to-Left (RTL) Support

RTL languages (Arabic, Hebrew, Persian, Urdu) require both logical and visual changes:

- **Logical text direction** — Svelte handles this via the `<html dir="..." >` attribute. Paraglide's `getTextDirection(locale)` returns `"rtl"` or `"ltr"`; the layout's root `+layout.svelte` sets the attribute on the `<html>` element.
- **CSS mirroring** — Use logical properties (`margin-inline-start` instead of `margin-left`, `padding-inline-end` instead of `padding-right`) instead of physical properties. CSS handles the flip automatically based on `dir`.
- **Icon mirroring** — Directional icons (back arrow, next arrow) must flip in RTL. Use `[dir="rtl"]` CSS selectors or SVG `transform` rules.
- **Flexbox/Grid auto-handling** — Modern CSS layout systems mostly handle RTL correctly when logical properties are used.

**Pre-v1.0 Task 6 audit result:** Arabic RTL review passed for the current web surface. The implementation uses logical CSS properties across the app shell, library/media grids, player controls, settings panels, and notification center. The mobile drawer and notification preference toggles use direction-aware `translateX()` variables. Back arrows are generated by CSS on `.back-link` and `.back-action` instead of being embedded in translation strings, rendering `←` in LTR and `→` in RTL. Headless Chrome CDP checks at 390px mobile width verified Arabic `dir="rtl"` and no horizontal overflow on dashboard, libraries, search, settings, notification center, system settings, and login routes. Player storyboard seek-preview X positioning remains physical by design because it is tied to pointer/time coordinates rather than UI reading direction.

**Activation policy:** RTL locales are not activated in the UI language switcher until they reach translation completeness AND pass a layout-review pass. A 90%-complete Arabic translation with broken RTL layout is worse than no Arabic at all. The first RTL locale likely ships in v1.1 or v1.2.

## Plural Rules and CLDR Concerns

Plural rules vary dramatically across languages — English has `one`/`other`, Arabic has `zero`/`one`/`two`/`few`/`many`/`other`, Chinese has only `other`. **This is exactly why plural decisions belong in translation files (Fluent/Paraglide), not in code.**

Pattern: never write `if count == 1 { "item" } else { "items" }` in code. Instead:

```ftl
# en/notifications.ftl
new-episodes =
    { $count ->
        [one] One new episode available
       *[other] { $count } new episodes available
    }
```

The Arabic translator provides the 6-form plural; the Chinese translator provides the 1-form plural; the code stays identical.

**Gender:** Currently no Dusgcue UI surface requires gender-aware strings. If future features (e.g., user mentions in shared playlists) introduce gender, Fluent's selector syntax handles it without code changes.

## Translation Workflow

### Platform: Weblate

**[Weblate](https://weblate.org/)** is the translation platform. Chosen over alternatives:

| Platform | Why not |
|---|---|
| Crowdin | Free for open source but proprietary SaaS; lock-in concerns. Weblate is open source, self-hostable. |
| Transifex | Commercial; per-seat pricing; not open source friendly at scale. |
| Direct GitHub PRs | Workable for small projects, but lacks translation memory, glossary, screenshot context, machine-translation aids that Weblate provides. |

**Weblate setup (deferred to v1.0 release prep):**

1. Self-host a Weblate instance at `translate.duskcue.dev` (or use Weblate Cloud free tier for open source)
2. Connect to Duskcue GitHub repo via webhooks
3. Configure components:
   - **Web client** — Inlang JSON format, source file `clients/web/messages/en.json`
   - **Server notifications** — Fluent format, source files `server/locales/en/*.ftl`
4. Translators contribute via Weblate UI (no git knowledge needed)
5. Weblate auto-submits PRs to GitHub when translations are approved
6. CI runs Paraglide build + Fluent validation on PR; merge if green

### Translation Quality Gates

- **Source string review** — English source strings reviewed by maintainers for clarity, brevity, context-comment presence
- **Translator attribution** — Weblate tracks per-translator contributions; contributors credited in release notes
- **Glossary** — Project-specific terms (e.g., "library", "scan", "transcode", "storyboard") defined once, used consistently across translations
- **Screenshots** — UI screenshots attached to translation strings for context (Paraglide + Inlang Sherlock extension supports this)
- **Machine translation suggestions** — Weblate integrates DeepL/Google Translate as suggestions; human translators approve/edit

### Locale Activation Threshold

A locale becomes selectable in the UI when:

1. **≥90% translation completeness** across all components (web client + server notifications)
2. **RTL layout review** (for RTL locales only) — maintainer verifies layout doesn't break
3. **Maintainer approval** — a Duskcue maintainer signs off, typically the contributor who drove the translation

Below 90%, the locale exists in Weblate but isn't selectable in the running app. Users in that locale see English with their translations in progress at Weblate.

## Edge Cases

### Mixed-Locale Households

A single Duskcue server may serve users with different locale preferences (e.g., English-speaking parent, German-speaking child). Each user's `users.metadata.locale` is independent; the notification renderer uses the *recipient's* locale, not the actor's. "Alice started watching Movie" — Alice is the actor (English), the notification recipient may be a German-speaking admin who sees "Alice hat begonnen, Movie anzuschauen".

### Locale-Aware Sorting

Library sort orders (`sort_title` column) are currently English-alphabetical. For non-Latin scripts (CJK, Arabic, Cyrillic), proper collation requires locale-aware Unicode collation. Postgres supports this via `COLLATE` clauses (`ORDER BY title COLLATE "de-x-icu"`). Phase 13+ may add locale-aware collation as a user preference; for v1.0, English-style ASCII sort is acceptable for all locales.

### Date/Time Display Consistency

Timestamps are stored as UTC ISO 8601. Display formatting is locale-aware: a `2026-06-19T15:30:00Z` event shows as "June 19, 2026 3:30 PM" for en-US, "19 June 2026 15:30" for en-GB, "19. Juni 2026, 15:30" for de, "١٩ يونيو ٢٠٢٦ ٣:٣٠ م" for ar. Both web client (`Intl.DateTimeFormat`) and server (ICU4X) handle this from the same UTC source.

### Right-to-Left Notification Email Templates

If Phase 13 adds email delivery, RTL emails need proper `dir="rtl"` on the `<html>` element of the email template, plus RTL-aware CSS. Most email clients honor this. Tested per-locale before activation.

### Locale Format Conversion

| Source | Format | Example |
|---|---|---|
| TMDb API | ISO 639-1 | `en`, `de`, `ja` |
| TMDb image language param | ISO 639-1 | `en,null` (English + language-neutral) |
| Subtitle files | ISO 639-1 or ISO 639-2/T | `en`, `eng`, `pt-BR` |
| Browser `Accept-Language` | BCP 47 | `en-US,en;q=0.9,de;q=0.8` |
| Fluent / Paraglide | BCP 47 (Unicode Language Identifier) | `en-US`, `de`, `zh-Hans-CN` |
| Duskcue `users.metadata.locale` | BCP 47 | `en-US`, `de`, `ar-SA` |

Internal Duscue canonical form is **BCP 47**. Conversion happens at integration boundaries (TMDb API adapter normalizes ISO 639-1 to BCP 47).

### Flutter Locale (Phase 16)

Flutter uses `Locale("en", "US")` and ARB files. Conversion from Weblate/Inlang JSON to ARB is a build-step export (Weblate supports ARB natively). Flutter's i18n story is independent from web/server — only the source-of-truth translations (Weblate) is shared.

### Partial Translations During Development

When a developer adds a new UI string in English (`clients/web/messages/en.json`), other locales are missing it. Paraglide's fallback chain handles this gracefully — the missing key falls back to English in non-English locales. Weblate surfaces the missing string for translators automatically.

### Locale Locked at Session Start

For SSR correctness, the locale is resolved once at the start of the request and held constant for the duration of the request. Mid-request locale changes (e.g., reading `Accept-Language` after reading URL prefix) would cause inconsistent rendering. Paraglide's middleware resolves locale once and stores it via `AsyncLocalStorage`.

## Key Decisions

1. **i18n-ready at v1.0, English source language** — Build the infrastructure now (zero runtime cost for English-only via Paraglide compiler); ship community translations post-launch as they reach 90% completeness. Avoids both "no i18n ever" (limits adoption) and "block v1.0 on translations" (impossible).
2. **Paraglide JS for web** — Officially recommended by SvelteKit docs. Compiler-based (small TV-browser bundles), type-safe, git-native workflow. `typesafe-i18n` rejected (unmaintained since author's passing); `svelte-i18n` rejected (runtime-based, less safe).
3. **Fluent for server, via `fluent-templates`** — Mozilla's system; linguistically expressive (plurals, gender, selectors move to translator files); used by Firefox and rust-lang.org. `rust-i18n` rejected (less expressive); `gettext` rejected (English-as-key makes typo fixes painful); `fluent-i18n` rejected (thread-local locale model is async-unsafe for concurrent per-user notification rendering — see "Crate Selection Rationale"). `fluent-templates` chosen for its `static_loader!` compile-time embedding and explicit per-call `lookup_with_args(&LanguageIdentifier, ...)` locale model.
4. **ICU4X for formatting** — CLDR-based number/date formatting on server; browser's native `Intl.*` on web (no JS library needed).
5. **English source language** — Matches development language; translations lag development so source-of-truth must be stable; partial translations are worse than full English.
6. **URL prefix + cookie locale routing** — Shareable localized URLs (`/de/dashboard`); sticky cookie for cross-session preference; server-side `Accept-Language` for first-visit negotiation.
7. **90% translation completeness activation threshold** — Below 90%, locale exists in Weblate but isn't UI-selectable. Mixed-language UI is worse than full English.
8. **Weblate for translation platform** — Open source, self-hostable, supports Fluent + Inlang JSON + ARB (Flutter). Crowdin/Transifex rejected (proprietary SaaS lock-in).
9. **Error responses stay English** — RFC 9457 `title`/`detail` are English-only; the `code` field (e.g., `AUTH_007`) is the programmatic identifier users search for. Translating detail provides little value and breaks copy-paste search.
10. **Media metadata is orthogonal** — TMDb returns localized metadata via `metadata_language` config; this is independent of UI i18n. A German-UI user can have English metadata if they prefer the original-language titles.
11. **RTL supported from infrastructure day 1, activated per-locale post-review** — CSS uses logical properties (`margin-inline-start`), Paraglide's `getTextDirection()` sets `<html dir>`, and directional back markers are generated in CSS so they mirror automatically. RTL locales activated only after translation review and the per-locale activation gate.
12. **Plurals belong in translation files, not code** — Never write `if count == 1` in code. Fluent/Paraglide handle per-language plural forms (English 2-form, Arabic 6-form, Chinese 1-form) in the translation files where translators control them.
13. **8 target locales for launch window** — `en` (source), `fr`, `de`, `es`, `it`, `ar`, `zh-Hans`, `zh-Hant` — covering ~4.3 billion speakers across 6 language families. Japanese, Korean, Portuguese, Hindi, Russian are likely Phase 2 additions. See "Target Locales" above.
14. **Informal register across all locales** — `tu` (FR/IT), `du` (DE), `tú` (ES). Matches Netflix/Spotify/Apple consumer-app convention; Duskcue is a personal/family media server. Decision locked at translation-start to avoid rework.
15. **AI-assisted initial translations + native review** — Initial `.ftl`/`.json` files for 7 non-English locales generated via AI, marked "needs native review," not UI-activated until a reviewer signs off. Pragmatic for a project without in-house translators; community refines via Weblate post-launch.
