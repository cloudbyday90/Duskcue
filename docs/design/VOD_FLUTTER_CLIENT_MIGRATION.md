## Existing decisions carried forward

Do not repeat the settled lifecycle interview. Positive complete acknowledgement selects protocol two; an initially unsupported server retains the legacy path; selected/uncertain new-lane work cannot downgrade. Capture exact origin/account/session/profile/context/credential/transport, generate UUIDv7 from authenticated database-time evidence, reuse one immutable identity/body per intended mutation and never automatically replay an uncertain command. Accepted work is server-owned.

One logical viewer/history survives same-item/file seek, tracks/quality and recovery. Adopt only the current immutable output and its server-supplied source-time origin. Renewal is independent of sequenced actual-output checkpoints. Keep the sixty-second lease, conclusive exact-UUID Start withdrawal, bounded final checkpoint before cleanup, at-most-once-per-second/sixty-second status monitoring and explicit reconciliation after uncertainty. Profile-only changes may retain cleanup-only identity; stronger scope changes clear the local record and rely on server retirement. Clearing local data never proves release. Production mounting/advertisement/caps and remaining online families stay separate until qualified.

## Confirmed mobile decisions

1. **Q1 confirmed:** implement and qualify Android interactive playback first with an isolated emulator. Provision a bounded owned test environment; leave iOS scaffold/device qualification, native ambient migration, offline playback and production caps separate.
2. **Q2 confirmed:** one app-scoped journal, at most four KiB, using existing secure storage. Store command IDs and exact scope identifiers, without credentials, media metadata or request bodies. Restart offers explicit status/cleanup recovery; no automatic Start or playback resume.
3. **Q3 confirmed:** support server-confirmed worker recovery. Generic plugin errors cannot establish decoder proof; automatic native decoder downgrade remains deferred until typed observation/probing is qualified.
4. **Q4 confirmed:** preserve existing independent interactive/ambient lifetimes with no automatic stop/handoff. Once both paths are migrated, simultaneous sessions represent two viewers. Platform audio focus remains separate from server cleanup; this increment claims neither tracked legacy ambient viewers nor production-wide cap enforcement.
5. **Q5 confirmed:** pause interactive video on lost activity, renew while Dart can execute, reconcile fresh status on return and require an explicit Play action. Disable uncontrolled plugin auto-resume; suspension or uncertainty never creates a new Start.
6. **Q6 confirmed:** qualify the bounded H.264/AAC, SDR/stereo, up-to-1080p video-encoded HLS lane first. Require current transcode permission, transcode-viewer capacity and physical encoder capacity. Compatible AAC may pass through, as clarified during the question round; direct/copied video, broader formats and unsupported HDR conversion remain outside this lane.

7. **Q7 confirmed:** retain video_player behind a bounded owned loopback HLS relay. Give the native player no server bearer; the relay owns exact-server output requests, redirect refusal, finite streaming limits and scope cancellation. The detailed [relay contract](../security/FLUTTER_HLS_RELAY.md) and [Android qualification contract](../ci/ANDROID_PLAYBACK_QUALIFICATION.md) form part of this proposal.

All seven mobile behavior/transport choices are settled. Final confirmation of the concrete scope, limits and qualification below remains pending.

## Decoder evidence boundary

The backend already accepts exact-output `native_decode` evidence and server-positive worker recovery. It checks current offer/source/tracks, descriptor/saved limits and the shared two-replacement budget; copied video requires smooth support, direct video rejects browser-only `hls_media`. A new wire format is not inherently required.

Locked video_player 2.11.1 with Android/AVFoundation implementations 2.10.0 flattens native failures into generic error text; the Dart value retains only the message. Android also internally handles a behind-live-window case. There is no exact-descriptor supported/smooth probe in this app. Parsing localized messages or reporting every `hasError` as a decoder failure would fabricate evidence. The provisional recommendation is server-positive worker recovery now, with generic media failure remaining unavailable/explicitly correctable; typed native decoder observation/probing is a separately qualified choice. The initial question asks the user to choose this scope.

## Native media transport findings and confirmed choice

Further read-only inspection found that locked video_player_android constructs a private `HttpVideoAsset` with `DefaultHttpDataSource.Factory`, sets cross-protocol redirects on and installs default HTTP headers. Its public creation API exposes URI/format/headers/user agent, without a data-source factory or per-request policy hook. The app declares Media3 1.10.1 while the plugin declares 1.9.2; final resolved dependency identity still needs build evidence. Cached 1.10.1 class inspection confirms a twenty-hop manual HTTP/HTTPS redirect loop that reapplies default request properties at each hop without an origin comparison. No current Duskcue redirect or credential exposure is alleged by that capability finding.

Dio's redirect option does control its Dart upstream transport, but does not control this native player. Initial output-URL validation therefore cannot establish exact-origin credentials for every native HLS request. Neither a superficial URL check nor a wrapper that delegates to the same redirecting data source establishes the boundary.

**Q7 confirmed:** keep video_player bearer-free behind a small app-owned loopback HLS relay. It will bind only literal loopback with an ephemeral in-memory capability, accept only the current viewer/output's allowlisted generated HLS resources, attach the captured bearer upstream, refuse redirects, preserve normal TLS verification and cancel on scope/output changes. It is not a provider connector, general proxy, download cache or decoder-proof adapter. No listener, credential or media URL would be restored from the journal. A plugin fork is not recommended.

The relay must own finite native connections, upstream requests, response bytes and application queues. Plain `HttpServer.bind` request-callback counters do not bound pre-header sockets: the Dart implementation accepts/parses them internally before emitting a request. Installed Dart 3.12.2 has a fixed one-MiB header-parser budget, while its ordinary socket reads aggregate available input rather than honoring an application-selected chunk size. `idleTimeout` is not an absolute per-accept header deadline. `HttpClient.maxConnectionsPerHost` also has an internal pending queue, so it cannot replace explicit caller admission. Socket-level acceptance/deadline ownership and a chosen finite HTTP subset must be named in the final design; no unsupported small-memory claim follows from high-level stream APIs alone.

The server's existing subset helps bound this design: generated rendition names are at most 64 ASCII alphanumeric/underscore/hyphen characters; media resources are `init.mp4` or numeric `seg_*.m4s` with bounded names. Existing rewriting binds references to the exact viewer/output, allows media-playlist URI tags only for `EXT-X-MAP`, and does not expose encrypted-HLS/key handling. The relay should reuse that narrow subset rather than accepting arbitrary upstream URI references. Its explicit admission, parser/streaming limits, storage/native completion semantics and actual-emulator attack/failure cases remain part of the pending concrete implementation contract.

## Concrete implementation contract

### Scope and composition

Implement the complete Start/status/seek/tracks/quality/checkpoint/renewal/worker-recovery/Close lifecycle for the existing Flutter interactive Android screen. Compose focused injected context/schema, HTTP, clock/UUID, journal, command/status, lease, checkpoint, reconfiguration/recovery, native-output, relay and screen-adapter files through the existing app-lifetime Riverpod providers. Route disposal must not discard accepted commands or retained cleanup. Keep the legacy branch before initial positive acknowledgement, offline playback and native ambient lifetimes separate. Do not add a new app, media engine, retry framework or normal server capability advertisement.

Reuse the existing no-store session-context endpoint and item-specific prepare capability. Require the complete four-feature acknowledgement. New-lane requests use captured original credentials and exact context headers; profile/account/server/credential transitions fence stale completions, and an old 401 cannot clear a newer session. Validate resource URLs, protocol, UUIDs, ETags and revisions before use. Unknown or partial acknowledgement refuses selection; a selected/uncertain protocol-two Start never downgrades. Normal startup still mounts no command owner/routes and enables no shared production cap.

Use a direct declaration of already locked/cached uuid 4.5.3, without a version upgrade. Generate UUIDv7 with fresh authenticated database time advanced by a monotonic clock and supplied secure randomness. Refresh time evidence before a new mutation when older than thirty seconds; refuse missing/invalid evidence. Preserve one immutable identity/body/condition per intended mutation. Restore known IDs only for explicit status or cleanup, never automatic Start or playback.

### Journal and native completion

Use one four-KiB, strict-schema app-scoped record with IDs and exact scope identifiers only. Keep it in a dedicated flutter_secure_storage namespace/prefix with reset-on-error and automatic migration disabled, separate from login storage. Capture the same options on every call. Errors, malformed records and failed writes/read-backs block mutations; never turn an exception into an empty journal or run a broad storage reset.

Serialize one actual storage operation at a time, with at most one retained clear/update obligation and no general queue. Complete and read back the ID before dispatching a mutation. A five-second observation deadline does not cancel native storage or permit another write to overtake it; retain actual completion and fence stale results. Credential/profile invalidation detaches media even when storage is unavailable.

The installed plugin uses asynchronous [Android SharedPreferences.apply](https://developer.android.com/reference/kotlin/android/content/SharedPreferences.Editor), checked through MCP primary-source research. Method completion/read-back is API acceptance and current readability, not fsync or guaranteed survival of abrupt process/power loss. A missing key cannot distinguish a first installation from externally lost state. Missing/lost state never proves server release, revives an old UUID or causes an automatic Start; server lease, retirement and confirmed cleanup remain authoritative. Qualify ordinary cold restart plus explicit storage-loss/failure behavior without claiming stronger persistence.

Keep one native-output owner through initialization, pause, source replacement and disposal. Capture actual output-bound source position and explicit playing intent independently of native events. Background/inactive pauses; disable plugin auto-resume, renew while Dart executes and require fresh status plus explicit Play on return. Expired/uncertain lease detaches output and never creates another Start. Generic media errors may trigger a bounded configuration read for positive worker recovery, explicit same-file reconfiguration/correction or Stop; they never manufacture decoder evidence.

Close samples a bounded final checkpoint, proceeds with exact-UUID withdrawal despite progress uncertainty and independently cancels/drains relay/native work. Observe actual platform/controller/transport completion; timeout or disposal error remains retained/quarantined in that process. Server settlement and local native completion are distinct. Keep server Stop/status available while local cleanup is uncertain; neither a missing registry entry nor a local journal clear proves physical cleanup. A fresh process never automatically reattaches the prior URL.

### Source lane and UI

Force video encoding for the selected protocol-two lane and advertise only bounded H.264/AAC SDR/stereo output up to 1080p, with a twelve-Mbit/s request ceiling or the stricter current policy/quality limit. Compatible AAC may pass through. Require current transcode permission, retained transcode-viewer capacity and physical encoder capacity; no permission or capacity bypass follows from the client preference. Reject unsupported HDR conversion and copied/direct/broader output instead of claiming qualified support. Qualify actual output codec/dimensions/timing against the built native runtime. Quality choices stay within this lane; stored preferences are hints rather than authority. Do not label an unqualified 4K/HEVC/HDR option as admitted.

Initial watch-resume uses a conditional same-viewer server seek before attachment; optimistic local seek values are not checkpoint evidence. Conditional changes remain in the admitted item/file with one viewer/history. Retire/drain old server output before replacement; cancel and observe the old native/relay owner before a replacement attachment. Track source stream indices belong to that admitted file and are not native track IDs. Preserve negotiated settings on seek/worker recovery; explicit tracks/quality obtain the current permitted plan. Paused intent survives all source transitions, including late events and changes during preparation.

Renew independently every fifteen seconds while held, subject to the existing sixty-second server lease. Send actual-output sequenced checkpoints at the existing fifteen-second cadence plus meaningful state transitions; coalesce one latest sample and reset its epoch on output revision change. Observe at most one status request per second for sixty seconds after known acceptance or explicit Check status; timeout leaves an explicit continuation, never mutation replay. Do not send viewer IDs to legacy heartbeat/Stop/probe/QoE endpoints. New-lane optional instrumentation must use correct attribution and bounded scoped transport; legacy advisory timers do not silently follow the new viewer.

Expose accepted/preparing/changing/recovering/paused/status-required/uncertain/cleanup states through AppStrings and Flutter semantics. Keep Back/Close, explicit status and cleanup/correction reachable with truthful progress versus resource-release messages. Preserve focus, large text, RTL layout and screen-reader semantics; do not infer spoken or physical-device fidelity from widget tests. Never show raw native errors containing bearer-free relay capabilities or upstream URLs.

### Limits and required evidence

Control/metadata/error JSON is at most 32 KiB; checkpoint/withdrawal requests at most one KiB; total control observation at most five seconds. Bound owned control HTTP operations to five: three regular operations and two reserved cleanup/settlement observations. Logical mutations remain serialized; an already dispatched Start/change can remain retained while explicit withdrawal proceeds. Renewal/checkpoint/status ownership remains single-flight, with no general request or mutation queue and one coalesced checkpoint. Cancelled-but-unconfirmed operations still consume their owned permit. Known accepted ownership persists beyond the observer. The [relay authority](../security/FLUTTER_HLS_RELAY.md) defines socket, manifest, range, streaming and deadline limits; SDK/TLS/parser overhead is explicitly separate from application queues and measured rather than falsely called a process-memory ceiling.

The [qualification authority](../ci/ANDROID_PLAYBACK_QUALIFICATION.md) defines managed serial Flutter/Gradle/emulator execution, isolated package/AVD/ADB identities, official SDK acquisition, real PostgreSQL/FFmpeg/native journeys and verified process/data cleanup. Existing app dependencies, Rust/Cargo, backend authority and root/resource limits remain unchanged except the direct edge to locked uuid. No test-only trust or bootstrap route is mounted in normal production.

All seven choices are settled; the shared-understanding confirmation covers this complete contract and both linked authorities. Implementation, build/runtime evidence and production enablement are not yet claimed. Windows Hypervisor Platform is currently disabled: prepare code/tests/APK first, then request a separate operator-controlled enable/restart handoff before actual accelerated emulator qualification. No OS feature change/reboot is authorized by this proposal alone. A package build or source-pattern check cannot satisfy the native runtime gate.
