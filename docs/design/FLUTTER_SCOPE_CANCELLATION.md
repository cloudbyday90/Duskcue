## Existing confirmed behavior

- A profile-only transition detaches output and may retain one cleanup-only record for the old viewer, because the same account/session can still request its cleanup. That record cannot deliver media or authorize a new viewer.
- Account, origin/server, session or credential transitions detach output and clear local recovery state. Cleanup of server resources remains server-owned; a new identity cannot borrow the old identity's cleanup authority.
- Scope changes, disposal, observation deadlines and cancelled reads never prove a server mutation did not happen. Do not replay Start, reconfiguration, renewal, Stop or withdrawal automatically. Exact IDs support explicit reconciliation under current authority.
- Background/lease uncertainty still requires current status and explicit Play. Position checkpoints and status reads do not renew a lease. Preserve independent renewal while its owner is current and Dart can run.
- A native/storage/network observation ending does not erase its unfinished resource ownership. Retain the existing finite admission, completion, quarantine and cleanup behavior. A late result cannot publish into another viewer, output or authenticated context.

These rules were accepted in the original migration and subsequent observer reviews. This increment qualifies and repairs their implementation boundaries.

## Official research and application

URLs were discovered through connected MCP search and their official pages retrieved on October 31. Public documentation guides design; inspected locked code governs version-specific behavior. The lock retains Flutter 3.47.8/Dart 3.13.7, Dio 5.10.0, flutter_secure_storage 10.3.4 and video_player 2.11.1. No dependency change is recommended.

- [Dart Future.timeout](https://api.flutter.dev/flutter/dart-async/Future/timeout.html) stops observation while the original future can still complete. Bind both observed result and retained completion to the exact originating work; do not free capacity from the observer's timeout alone.
- [StreamSubscription.cancel](https://api.dart.dev/dart-async/StreamSubscription/cancel.html) returns a cleanup future. Await owned subscription cleanup where release depends on it. An API cancellation request alone is not a physical socket-close acknowledgement.
- [Dio CancelToken](https://pub.dev/documentation/dio/latest/dio/CancelToken-class.html) cancels all requests sharing that token. Use per-operation cancellation for a single observer; reserve whole-transport cancellation for its existing scope/disposal boundary. Retain the SDK operation's completion and independently observe socket closure in qualification; do not infer kernel completion solely from a cancellation signal.
- [Flutter lifecycle states](https://api.flutter.dev/flutter/dart-ui/AppLifecycleState.html) can be skipped when an app is terminated. [Android activity guidance](https://developer.android.com/guide/components/activities/activity-lifecycle.html) describes releasing resources as activity state changes. Keep server leases, durable receipts and cold-restart reconciliation authoritative; lifecycle callbacks cannot promise a final checkpoint or Stop.
- [Flutter integration testing](https://docs.flutter.dev/cookbook/testing/integration/introduction) distinguishes whole-app/device tests from units and notes that integration_test cannot itself operate native platform UI. Reuse the isolated emulator and exact owned ADB actions; do not add a test framework just to exercise existing provider/channel seams.
- [W3C status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html?trk=article-ssr-frontend-pulse_little-text-block) and [focus order](https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html) support truthful programmatic status and meaningful navigation. Preserve Close/status recovery where authorized, do not steal focus on late completions, and do not expose old account/profile information after a transition. Widget semantics and emulator tests do not establish spoken TalkBack or complete physical-device accessibility.

## Options and recommendation

| Option | Pros | Cons / recommendation |
| --- | --- | --- |
| Add deterministic tests only | Smallest increment; fast repeatable race reproduction | Leaves production-provider/native storage and delivery transitions unqualified; offered as the narrower Q1 choice |
| Complete scoped lifecycle ownership and real provider qualification | Addresses asynchronous state/storage/resource boundaries together; verifies the actual app wiring | Requires careful ownership refactoring and additional real backend/emulator journeys; recommended |
| Recreate controllers/storage freely on scope changes | Superficially simpler reset | Does not fence unfinished native/storage work; can produce competing ownership and stale journal effects; reject |
| Add cancellation/retry packages or migrate the player stack | Could offer generic helpers | Does not establish application scope or conclusive server outcomes; adds unrelated dependency/qualification surface; unnecessary |

Recommended stack: existing locked Flutter/Riverpod services; a small injected app-lifetime ownership service for journal/native obligations; exact context/epoch/Start/output tickets; existing retained-operation and strict Dio transport primitives; current server context/conditional commands/withdrawal; existing secure journal namespace and bearer-free relay; deterministic HTTP/native/storage seams plus actual isolated Android/PostgreSQL/HTTP/FFmpeg qualification. Prefer composable provider-owned services over a monolithic coordinator or process-global playback singleton.

## Proposed implementation and qualification

Once scope is confirmed, extract ownership and invalidation into focused service files. Preserve the existing controller/public contracts while binding every post-await publication and follow-up action to its originating context. Fence pending Start storage even before a visible record exists. Serialize actual app-journal work across coordinator replacement, including invalidation clears; retain failures and pending completion explicitly. Preserve the distinction between profile cleanup-only authority and stronger-boundary clearing. Complete status/read ownership through its retained transport handle. Bind late native cleanup/attachment errors and play intent to their exact owner; never clear a newer owner's state.

No new wire protocol, production route, wider credential trust, automatic retry, queue, background worker or increased resource limit is proposed. Keep the one 4-KiB journal, three regular/two cleanup HTTP permits, 32-KiB JSON, five-second control/storage observations, thirty-second native attachment, sixty-second lease/fifteen-second renewal, current relay budgets and root/VM limits. Any required change to those bounds must be reviewed explicitly, not hidden in a retry.

Deterministic/loopback qualification should cover each boundary before and after dispatch: pending Start journal/context/prepare, accepted Start/status, configuration/checkpoint/renewal, Stop/withdrawal, paced/in-flight reads, real subscription/socket cancellation, delayed journal read/write/clear/readback and delayed native initialization/disposal. Cross scope during success, failure, timeout and cancellation; then create a new viewer and prove old completions cannot adopt it, erase its journal, renew its lease, change intent or publish a stale error. Include production-provider subscription tests and accessible truthful cleanup/status controls.

The recommended native addition uses the actual API client, session notifier and coordinator provider, not an immutable identity/coordinator override. The production router already exposes session-context, standard-profile switching and logout. A disposable fixture can seed another legitimate profile/session/account using existing helpers, without a production bypass route. A small allowlisted qualification-only held-response witness can exercise profile transition during an actual read/control and a stronger session/credential transition while real secure-storage acknowledgement is retained. State exactly whether a seam delays invocation, acknowledgement or physical native work; do not manufacture a native failure or claim those are equivalent.

Keep all existing eight journeys and their identity/budget/cleanup assertions. Add separately attributed scope journeys with exact viewer/history/Start counts, fresh context, old-output refusal and no replay. If an alternate owned origin uses the same backend, describe it as origin-boundary evidence rather than two independent servers. Do not instantiate the existing browser_paced fixture twice in one database; it creates default test partitions unconditionally. New profiles/sessions/actors must be provisioned through small qualification helpers with real server token/hash and policy rules. Full relay adversarial/backpressure/output-format qualification stays next.

Run managed serial tests/analysis/format, relevant host checks, both APKs and the full actual native/backend suite on frozen inputs. Preserve existing three-minute scenario/thirty-minute suite and host commit guards. Current compiler checkpoints can be reused only after input/executable validation; runtime cases always execute fresh. No service interruption is authorized by this document. Apply [repository cleanup](../../.agents/skills/duskcue-repository-cleanup/SKILL.md) after actual owner completion, retaining compact evidence and useful current compiler/SDK/APK inputs. The previous Docker restart approval is consumed.
