## Confirmed product decisions

1. Deliver three separate shared Settings surfaces: administrator assignment/destination/manual refresh with a paginated household picker; delegated standard-profile/cap controls linked from Household management; and a separate server-operator refresh-enable control. Preserve their independent permission/proof boundaries. Playback, scheduling and native passkeys stay deferred.
2. Drafts stay in screen memory, with discard confirmation before leaving. Submitted URL/origin/IP values clear on submission and scope changes. Unlock uses the existing owner-security screen and never resumes a mutation automatically. Self-household administrator saves revoke that administrator's grant; the next sensitive action requires explicit unlock again.
3. Assignment replacement, deletion and destination revocation receive focused consequence confirmations. Ordinary saves use validation plus an explicit Save button. Rotation and replacement remain separate operations.
4. Accepted refresh monitoring uses visible-screen metadata checks at five-second intervals for at most five minutes, stopping on completion, error, hidden page or scope change. Explicit Check status remains available. Neither a monitoring timeout nor browser disconnection means the server attempt failed; no POST replay is permitted.
5. Definitive validation errors retain nonsensitive edits for correction. Stale context/version and uncertain outcomes disable further writes until explicit metadata reload and review. Submitted source fields still clear; there is no automatic merge or retry.

## Source findings

Three read-only fact explorations inspected assignment authority, destination/refresh ownership and existing client infrastructure. They changed no files or credentials and ran no heavy checks.

- A user account is a household. Administration requires current `can_manage_users`; writes also require the acting administrator's fresh own-account grant. Owner policy routes are self-household only and require the exact delegated permission plus a fresh activated owner grant. The global refresh switch requires current `can_manage_server`, with proof on writes. Cached capabilities are navigation hints, never write authority.
- There is no administrator route to set another household's individual profile choices. New profile access defaults disabled; Kids are ineligible. Owner profile access and a stricter owner Live TV cap are independent default-off delegations. Stored caps are configuration, not qualified shared playback admission.
- Source URLs, destination origins and pinned IPs are encrypted/write-only. Reads return presence, transports, approval counts, identity/generation and policy only, without even masked source values. UI reload cannot prefill those fields. Saving does no source I/O and does not establish upstream authentication, source membership or playback readiness.
- Every administrator assignment/policy/credential/destination change revokes the target household's grants and ceremonies, including the acting grant on self-administration. Configure also advances source generation. Rotation preserves assignment identity and policy, retaining only valid same-origin approvals; replacement resets owner choices/approvals and creates a UUIDv7 identity. A fresh generation requires a new import before saved catalog reuse.
- Assignment, owner policy, refresh admission and global control have distinct strong ETags. Mutations cannot reuse another representation's validator or synthesize one from a displayed revision. Existing i64 revisions and attempt sequences are JSON numbers, unlike decimal-string session-context revisions; ordinary JSON parsing can round them.
- At the research baseline, assignment/refresh handlers constructed an unbound `Scope::from(...)`; `X-Session-Context` was wired only to owner-security handlers. These forms need a focused integration of that check into current Live TV transactions; merely sending the header is insufficient.
- The API core's raw `returnResponse` path bypasses bounded/error parsing and releases scope listeners before body materialization. It is unsuitable unchanged for a body-plus-ETag management contract.
- `/settings/users` currently reads only the default first page and has no Live TV detail action. `GET /users` supports page/page_size (maximum 100), status and role filters, but no name search. Desktop route/deep-link policy already supports one settings slug, including the three proposed routes below; no generic admin-route widening is needed.
- A 202 is durable acceptance, not completion. There is one global import lease and no queue/history API/individual cancel route. The status resource distinguishes current, never imported, not current and unfinished/unowned uncertainty. Last-good snapshot evidence can remain after a failed latest attempt; a success alone does not establish current-source authority.
- Ordinary grant expiry does not cancel accepted work. The existing Lock management action deletes its session grant/ceremonies but does not change the owner-authority revision, so it does not cancel an accepted refresh. Preserve this behavior and label it accurately. Global disable prevents admission and cancels active work; it does not erase last-good data or repair quarantined cleanup.

## Alternatives, pros and cons

| Approach | Pros | Cons | Recommendation |
|---|---|---|---|
| Three separate settings surfaces | Completes catalog setup while keeping admin, owner and operator authority visible; uses current desktop route policy. | More explicit navigation than one universal form. | Confirmed. |
| One universal administrator/owner wizard | Fewer pages. | Blurs target household versus acting account, grant revocation and independent operator authority. | Reject. |
| Separate explicit unlock and mutation steps | Reuses qualified credential adoption; no retained source draft through proof routing or automatic continuation. | Self-administration can require repeated proof and re-entry of source fields. | Confirmed. |
| Embedded unlock with automatic wizard continuation | Less repetition. | New credential/draft ownership, origin and resumption semantics would need independent design/qualification. | Deferred. |

| Bounded visible status monitoring | Gives useful progress without background work or a new transport. | Status remains observational and stops after five minutes or when hidden. | Confirmed. |
| Automatic mutation retry or source-secret readback | Could appear simpler. | Can repeat a committed refresh or expose credentials that existing contracts intentionally never return. | Excluded. |

Recommended stack: locked Svelte 5/SvelteKit 2/Paraglide, semantic CSS and native HTML forms/dialogs, small composable management schema/HTTP/draft/command/monitor/controllers, current auth owner and native keyring, and existing Rust/Axum/SQLx/PostgreSQL/ring/Hyper/Tokio-Rustls services. ## Confirmed implementation contract

### Surfaces and authority

Use `/settings/live-tv` for administrator setup, `/settings/household-live-tv` for delegated self-household policy, and `/settings/live-tv-control` for the server-operator switch. Link the first/third through current capability-based Settings/admin navigation hints; link self-household policy through Household management. Direct entries are server-authorized. All three require a selected standard profile; Kids issue no new management requests. Do not broaden desktop routes or native IPC permissions. Native passkey-only users retain hosted-browser guidance, with no cross-session grant transfer.

Use a bounded active-household picker with twenty accounts per page, explicit Previous/Next/First and safe text labels, without claiming unsupported server name search. Keep selected target and all page/draft/attempt state in memory. Changing target uses the same dirty/busy transition gate as navigation. Do not use URL query input to select a write target automatically. The signed-in administrator proves their own account; target households do not supply their factors to that administrator.

### Backend binding integration

Expose a deliberate shared owner-service scope parser and use it in all current assignment/owner-profile/control/refresh resource/status/start handlers. Supplied `X-Session-Context` is checked under current existing transaction locks before side effects or acceptance. The bound context is always the initiating account/session/profile, not the target household. Preserve unbound legacy callers' existing authority and all backend permission/grant/precondition checks. Reuse fixed OWNER_005/400 and OWNER_007/409 refusals. Add no credential, migration, grant duration or CSRF/origin-policy change.

### Bounded HTTP and exact metadata

Add an opt-in bounded result mode to the API core that materializes JSON and selected response metadata before disposing abort/scope ownership. Preserve unrelated callers and the existing raw-response contract. New management calls use a fifteen-second HTTP deadline, no-store, a 256-KiB success/error body ceiling, strict UTF-8, fixed problem-code allowlists and the existing sixteen-KiB request-body ceiling. Keep conditional-header input within the established 1,024-byte bound. Disallow API redirects for the new management calls. Header metadata is selected and bounded; do not expose an arbitrary raw Response to screen controllers.

Capture the exact strong ETag from each representation, validate its shape/size, and retain it only with its typed body, acting context, selected target and resource kind. Do not reuse assignment, owner, refresh and global-control ETags. Do not send conditional GETs or accept 304 as a new editable representation in this first UI. Creation uses only If-None-Match:*. Existing mutations use that resource's exact If-Match. Missing/weak/malformed/unrelated validators never enable Save.

Project revision/source-generation/attempt-sequence integer tokens to exact nonnegative decimal strings through a focused reviver using original source text. Validate i64 bounds and actual browser/native behavior. On engines without source text, accept only safe integer values and refuse unsafe ones; never silently round. Keep bounded counts, caps, pages and pin indexes as checked safe integers. Do not change the existing backend numeric wire format, reserialize a representation to derive ETags, or introduce another JSON library.

Read authoritative session context before metadata and validate the actual account/session/profile at publication. Guard every result by frontend auth revision, selected server, selected profile, selected household and controller epoch. Discard stale/canceled/failed reads, ETags and actionable state. Compare administrator assignment and refresh resource identity/revision/generation before combining them into readiness. Owner profile pages use twenty entries and at most sixty-four cursor-history entries, with assignment-revision checks between pages; this is current keyset pagination, not a claim of immutable membership across profile creation/deletion.

### Administrator setup and source forms

Offer explicit create, configure, rotate, replace, approve playlist destination, approve guide destination, revoke each destination and delete actions against their existing DTOs. Display only backend metadata. Existing values are never prefilled with secret placeholders or exported for editing. Creation and configuration use explicit policy fields with restrictive defaults; null means no additional cap at that layer, never unlimited runtime playback. Do not imply an administrator can directly toggle a target household's individual profiles.

Source URL fields preserve exact supplied bytes and enforce the 4,096-UTF-8-byte validator boundary, without synthesizing Dispatcharr routes. Origin/IP approval accepts a deliberately supplied HTTP(S) origin and one through eight ordered, unique bare IP literals for that feed. Backend classification and origin agreement remain authoritative. There is no DNS discovery, redirect/proxy fallback, certificate-verification checkbox, private-CA input, stream/logo fetch or automatic connection failover. After reload, show only approved counts and offer numbered address choices in the saved order; actual addresses are not read back. Each refresh requires explicit playlist/guide pin selection within the current counts.

Explain policy/generation effects before action. Configure and source/destination changes can make the old catalog unavailable until a new import; rotation preserves assignment/policy while replacement resets owner choices and approvals. After a successful self-household administrator write, show that management is locked for the next action and require explicit unlock. Do not assume the preceding grant survives. A save, approval, enabled assignment, successful import and production playback availability are separate facts. Do not treat hardcoded assignment `network_checked:false`/`playback_available:false` as a failed refresh.

### Owner policy and operator control

Owner policy reads/writes require the current activated self-household grant and server-reported delegation/allowance. Show only owned profile metadata; Kids controls are ineligible/disabled. New standard profiles remain disabled until explicitly granted. Each toggle and cap save is explicit and conditional on the owner assignment representation; profile-page ETags are not mutation validators. Recheck current assignment revision before publishing a page or writing a choice. Honor independently withdrawn delegation and retained stricter choices. Describe configured ceilings without claiming production stream-cap enforcement.

The operator control uses its dedicated GET/PUT resource, current CanManageServer plus proof on writes and its own ETag. Show default-off state truthfully. Disabling is a consequential global action: explain that it stops new starts and cancels active refreshes while retaining last-good data. Do not route it through generic JSON settings or represent it as an individual household Cancel button. A failed/quarantined service is not repaired by enabling again.

### Draft, proof and command ownership

Use small scoped controllers and a composable retained command owner shared across the three surfaces for the app auth lifetime. Permit at most one pending management mutation per client, with no queue, and coordinate with pending credential adoption. Retain a submitted operation through bounded response settlement even if its screen is disposed; cancel metadata reads/monitoring separately. Reject or ignore late results from an older server/account/profile/target, without changing newer credentials. Do not retain raw source values in observable command metadata, storage, URLs, notices, analytics or logs.

Use the existing navigation guard, native dialogs and before-unload behavior for dirty/busy forms, profile changes and server switches. Clear all screen state on teardown/pagehide; browser-history restoration begins fresh. Keep source fields in memory only, permit paste, request no source-field autofill/spellcheck and clear submitted values at dispatch. Preserve ordinary owner-password manager support on its separate screen. Clear source drafts when management proof expires or scope changes. Nonsensitive drafts survive only definitive validation refusal on the same current representation. Consequential confirmation dialogs explain effects, start at a safe focus choice, support Escape and restore logical focus; routine saves do not add an unnecessary confirmation.

Unlock never automatically resubmits or resumes the intended mutation. Re-enter through the current screen and explicitly review current metadata. Stale 409/412/428, authority refusal, unrecognized/malformed success, transport/deadline loss or an uncertain outcome clears actionable versions and blocks further writes until explicit reload/review. Clear protected owner data on refusal. Treat known owner-proof failure separately from independently confirmed viewing-session expiry, preserving newer-session guards. Respect valid Retry-After before explicit recovery; never invent a lockout time or automatically retry a mutation. An abort or a missing response does not prove rollback.

### Accepted work and monitoring

Validate 202 acceptance shape and the matching Location/status URL against the exact selected household and returned UUIDv7 attempt. Never pass an arbitrary returned URL into generic bearer fetch or duplicate its `/api/v1` prefix. Construct the known status request from validated IDs and fixed route parts. Keep acceptance, progress and last-good data visibly distinct.

Check an accepted attempt immediately, then at nonoverlapping five-second intervals only while visible, for at most five minutes. Stop on terminal/uncertain/not-current observation, any request error, page hide, navigation or scope change; leave explicit Check status available. Do not resume watching or POST automatically after restore. A stop-watching action stops only client observation. Ordinary grant expiry can block new writes while permission-authorized status reads continue. Lock management is not cancellation of already accepted work.

For an unacknowledged start, provide explicit latest-status reconciliation without inventing the lost attempt identity or claiming the latest record is necessarily that user's command. A mismatched expected attempt is not its historical outcome. An unfinished unowned record is uncertain and is never restarted. Preserve last-good attribution and current-source evidence from the server rather than inferring current availability from a latest success/count alone.

### Accessibility, qualification and scope

Use native labeled/grouped controls and existing semantic tokens, fixed per-field errors plus accessible summaries, meaningful live status without polling chatter, localized timestamps/device zone, plaintext user labels, fallback language annotations, keyboard-visible focus and modal focus restoration. Qualify reflow at 320 CSS pixels, 400% actual native zoom, RTL, supported contrast and screen exit/focus ownership. Do not claim full WCAG/NIST conformance or spoken assistive-technology/hardware-authenticator coverage from these checks.

Qualification includes bounded body-plus-header/cancellation tests, exact integers above 2^53, wrong-resource ETags, unknown errors, stale/newer context races, write ownership/no replay, draft/confirmation/expiry, owner/delegation/Kids, ordered pin choices and status uncertainty/monitor stop conditions. Use actual production-route PostgreSQL checks for every newly bound handler family and a real browser-to-Rust/database setup/import flow with controlled HTTP M3U/XMLTV, encrypted write-only storage, operator enable, accepted status and last-good evidence. There must be no production bypass route, test CA in ordinary builds or external provider connection. Reuse actual isolated Tauri with both selected origins, real OS keyring/transport, management journeys/accessibility captures and verified fixture/process cleanup. Existing owner, assignment and relevant refresh regressions remain intact.

Run heavy tests/builds serially under unchanged resource guards, workers, pool/container limits and root deadlines. Reuse locked dependencies, Rust SDK and approved legal headers only; no explanatory source comments. Update this authority, related domain references, BUILD_ORDER and PROJECT with exact code/evidence/outcomes, then commit/push all changes on main without release, PR merge or deployment. Production playback/shared admission, real Dispatcharr playback, scheduling, Kids rating policy, native passkeys, ordinary passkey-login repair, favorites/order/logos and independent notifications remain separately scoped.

## Implementation notes

The shared client uses focused schema, HTTP, session, scope, retained-command, monitoring, form-validation and administrator/owner/operator controller modules. Components contain labeled controls and presentation; existing backend services retain permission, proof, encryption, revocation and conditional-write authority. The root auth lifetime owns one retained command slot and coordinates it with credential replacement. Disposing a screen cancels reads and observation, while a submitted command settles under its captured context without publishing into a newer screen.

The API core gains only an opt-in bounded body-plus-selected-header result. Unexpected successful media types are canceled without buffering; this mode cannot opt into an unbounded text/raw response. Its normal raw-response behavior is unchanged. Management revisions use original JSON integer source text; caps/counts remain checked integers and strong validators remain opaque. Browser source drafts are cleared at dispatch, expiry and scope exit. Accepted attempts are tracked by validated UUIDv7 identity; no returned arbitrary URL is fetched. An unacknowledged new start discards any previously expected attempt identity before explicit latest-status reconciliation.
