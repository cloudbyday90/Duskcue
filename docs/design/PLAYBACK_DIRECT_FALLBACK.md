# Authenticated direct-play fallback

Status: complete for the qualified SDR handoff, 18 October 2026. This document owns the direct-file decoder handoff. [Playback recovery](PLAYBACK_RECOVERY.md) owns the shared attempt budget and HLS worker lifecycle; [compatibility](PLAYBACK_COMPATIBILITY.md) owns ordinary format admission.

## Accepted scope

Continue the confirmed automatic recovery, source preservation and disclosed degradation policy for web and the existing desktop player. A current native `MEDIA_ERR_DECODE` may promote an eligible direct-file session to a compatible HLS generation without creating a new logical play session. Network errors, authorization failures, aborted playback and ambiguous unsupported-source errors cannot request this promotion. Sources and selected stream identities remain unchanged. No release or second native playback engine is introduced.

Same-origin cookie authentication currently permits native direct-file delivery in the web client. Desktop bearer authentication already requires header-authenticated HLS; preserve that requirement. Shared client adoption and controls apply to desktop, but a desktop native-direct qualification must not remove authentication to create an artificial scenario.

The repository design-review workflow was applied to the existing confirmed scope and the server/client audits. The user's instruction to begin the previously recommended direct fallback authorizes this increment. No additional product choice was identified; fixed output settings, revision validation and isolated testing implement the accepted source, quality, authorization and retry constraints.

## Official research and alternatives

Official sources were discovered through connected search/GitHub services on 18 October 2026. The [HTML media standard](https://html.spec.whatwg.org/dev/media.html) distinguishes network error 2, decode error 3 and unsupported source 4. Error 3 does not identify the failed audio/video stream. A browser hint is scoped playback evidence, never authorization or proof of source corruption. [Media Capabilities](https://www.w3.org/TR/2026/WD-media-capabilities-20260609/) distinguishes file and media-source delivery and reports support, smoothness and power efficiency separately. Query the actual bounded replacement configuration; neither user-agent names nor hls.js availability prove decoder support. Real presented frames and selected audio remain the acceptance evidence.

The [Web Audio specification](https://www.w3.org/TR/webaudio/) defines frequency measurements over recent FFT samples and smoothing across blocks. The browser qualifier disables smoothing and requires a running audio context, at least 500 ms after HLS attachment, a peak above -60 dB and the selected 880 Hz frequency. This is numerical decoded-audio evidence, not an observation of sound at physical speakers.

[FFmpeg's command documentation](https://www.ffmpeg.org/ffmpeg.html) distinguishes input and output option placement and the `-r`/`-fps_mode` output controls. The fixed replacement profile applies its level, frame rate, AAC profile and sample rate after the input and verifies the encoded fragment. The small SDR fixture uses the documented [`setparams` filter](https://ffmpeg.org/ffmpeg-filters.html) and a separate probe to establish its intended metadata; it is not an HDR fidelity reference.

[hls.js support detection](https://hlsjs.video-dev.org/api-docs/hls.js.hls.issupported) is one admission prerequisite alongside exact MSE/Media Capabilities checks. [Playwright's media-codec guidance](https://playwright.dev/docs/browsers#media-codecs) supports using an installed branded browser for proprietary-codec qualification. [Tauri's webview guidance](https://v2.tauri.app/reference/webview-versions/) explains the separate platform runtime boundary; the installed Chrome result is accompanied by its own isolated WebView2 execution record.

| Option | Benefit | Cost or boundary |
| --- | --- | --- |
| Retry the direct URL | Low resource cost | Can repeat the same decoder failure |
| HLS remux | Preserves compressed streams | Retains the codec or damaged packets that failed |
| Encode only video | Lower CPU than encoding both streams | A generic decode error can originate in audio |
| Bounded software H.264/AAC encode | Reuses the managed sandbox, avoids hardware ambiguity and provides a known output envelope | CPU cost, rebuffering, lossy conversion, possible downmix/resolution/frame-rate reduction |
| Add a desktop playback engine | Could expand native codec support | Separate packaging, lifecycle, authentication and platform qualification; outside this increment |

## Recommended stack and contract

1. The shared web/desktop start request opts in with `direct_recovery_protocol: 1`. Only that understood protocol creates a server-owned UUID source revision and bounded versioned context at direct-play admission. Retain the healthy file identity (file ID/path/size, database update time, filesystem modification time and normalized probe hash), resolved selected tracks, original capability/quality limits and an optional admitted fallback. Failure to prepare a fallback must not reject otherwise valid native playback, including HDR.
2. Offer a private-plan-free capability descriptor for a fixed SDR H.264 High level 4.0, eight-bit, at-most-1080p/30fps and AAC-LC 48 kHz at-most-stereo output. Respect lower source/device/quality limits. Enforce the advertised codec settings in the encoder and retain them through seek and recovery. Use software encoding for this promotion, so it spends one attempt without hidden hardware startup retries. Refuse unsupported HDR conversion and missing/inconsistent source context.
3. On a fatal native decode event, capture source position and play intent before detaching. Probe exact media-source video/audio support with a bounded deadline, including MSE codec support. Unknown, rejected or stale evidence cannot allocate output.
4. Send the current direct revision, existing recovery hint and bounded capability confirmation through heartbeat. Under the existing session row lock, require the original active profile, current revision and unchanged healthy file, then revalidate media access on the owned connection. Only server-derived parameters reach FFmpeg.
5. Reserve one of the existing two automatic attempts, start a fresh HLS generation at the confirmed absolute source position and hold pending ownership through commit. Preserve selected tracks and logical session; disclose conversion. Failed admission/startup becomes explicit and cannot loop. Later HLS recovery uses the same budget.
6. Deliver canonical stream decision, generation, source offset and recovery state. Guard asynchronous probe, send and adoption by session, profile/context and source revision. Explicit direct seeks drain outstanding heartbeat work, rotate the server revision and invalidate earlier probes; stop and context changes invalidate adoption. Retain pause intent.

Sessions started without protocol version 1, including omitted or unknown versions, keep ordinary direct bookkeeping and cannot opt themselves into fallback through heartbeat. This protects existing Flutter, Android/Fire TV and native ambient callers as well as older web/desktop builds. Only opted-in sessions require revision echoes: a missing/stale revision returns canonical state without changing checkpoints or spending attempts. New independent clients must implement version-1 source/revision ownership before advertising it. No request accepts paths, raw diagnostics, shell arguments or arbitrary encoder settings.

## Implementation ownership

| Layer | Modules | Responsibility |
| --- | --- | --- |
| Rust server | `playback/direct`, `direct_admission`, `direct_recovery`, `media_source`; transcoding `output_profile` | Authorization, immutable admission context, transactional promotion and actual encoder settings |
| Shared ES Module JavaScript | `playback/capabilities.js`, `heartbeat.js`, `source.js`, `stores/player.js` | Browser capability evidence, source events and guarded canonical adoption for web/desktop |
| Node ES Modules (`.mjs`) | `scripts/qualification/direct-*`, `scripts/testing-memory/direct-inputs.mjs` | Owned local test transport, artifact identity, resource bounds and proof validation |
| Existing TypeScript test suites | `clients/web/tests/unit` and `tests/e2e` | Typed unit and browser regressions using the repository's existing runners |

These are distinct runtime and test responsibilities. The JavaScript/TypeScript code uses ES Modules throughout; the Rust server retains Rust modules. The private admission and encoder decisions have one server owner.

The existing atomic transaction pattern durably records committed recovery outcomes. Cancellation or a database rollback before commit retires unpublished output and rolls back its attempt reservation; this does not charge every abandoned process start durably. The shared client sends one automatic hint per direct revision and does not automatically replay a failed request. Existing API rate limits, worker capacity and startup deadlines still apply. Charging canceled, unpublished admissions would require a separate durable lease design rather than claiming a rolled-back transaction persisted its reservation.
