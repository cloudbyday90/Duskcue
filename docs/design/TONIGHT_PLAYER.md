### Per-player runtime contract — October 3, 2026

The runtime composes the existing preference facade, full-file track resolver, fresh playback-entry loader, and mature player store. It owns no DOM, fullscreen, source attachment, autoplay timer, or transport controls. Each `createPlaybackRuntime({ player, preferences, loadEntry, getPlayerState, requiresAuthenticatedSource, onChange })` instance has its own operation generation, cancellation signal, confirmed profile context, applied selection, one-off overrides, and cleanup.

The API is `start(entry, { profileId, context, signal })`, `restart({ audio, subtitle, quality })`, `transition(nextEpisode, { signal, profileId })`, `refreshPreferences()`, `retry()`, `getState()`, and `dispose()`. Initial `context` is `{ serverOrigin, userId }`, with an optional device ID supplied by the existing preference facade. Initial entries contain actual `item`, full healthy `file`, `startPositionMs`, and validated `destination`. Published state exposes `item`, `file`, `preferencesReady`, `autoplayEnabled`, `tracks`, `selection`, `overrides`, `quality`, `fallback`, `error`, `loading`, and `destination`.

Load the confirmed preference scope before initial playback; a failed preference read blocks playback and autoplay, exposing an explicit recoverable error. Successful same-scope saves update the confirmed autoplay flag without an extra API read. Audio and subtitles already applied to a running source remain unchanged until a deliberate restart or transition. Device quality defaults initialize playback; one-off choices do not save profile or device settings.

Restart audio/subtitle values are objects returned by `createTrackOverride(kind, actualTrackOrNull, fullFile.id)`. Omitted values retain the existing one-off choice; `null` clears an override back to saved defaults. A null track means explicit source-default audio or subtitles Off. Quality uses the existing `{ quality_mode: 'auto' | 'maximum' | 'manual', max_streaming_bitrate }` device DTO. Restarts revalidate the exact healthy file and use the current player position after that read; next episodes re-read actual metadata, healthy files, and watch state. Semantic language/accessibility overrides carry across files, while unknown-language or unavailable matches produce a visible fallback flag. Completed items begin at zero.

All playback starts receive the runtime operation signal and actual audio/subtitle indexes. Bearer authentication forces the existing transcode path. After a nonzero HLS start, await the real `player.seek(position, { signal })` before publishing success and clearing runtime loading. Direct media retains its existing metadata-driven DOM seek. Failed seeks reject recoverably and pause only the still-owned session. Session ownership and generation checks surround all asynchronous boundaries; obsolete completions cannot publish a destination, restart or pause a newer session, or issue an unconditional stop. Disposal unsubscribes preferences and cancels only the instance's operation.

The official [WAI media-player guidance](https://www.w3.org/WAI/media/av/player/) and [WCAG status-message guidance](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html), researched October 3, 2026, support keyboard-operable caption/description choices and programmatically exposed dynamic status. Presentation remains responsible for named native controls, visible focus, and stable fallback/error announcements. The runtime emits semantic state changes without per-second speech or focus changes. Blocking initial playback until preferences are confirmed, explicit Retry, semantic one-off carry, and the default quality mode are product decisions; they are not separate WCAG requirements.

### Heartbeat settlement boundary — October 7, 2026

Reviewed the current official [WHATWG timer standard](https://html.spec.whatwg.org/multipage/timers-and-user-prompts.html) and [published ECMAScript edition overview](https://ecma-international.org/publications-and-standards/standards/ecma-262/) on October 7. Timer cancellation controls future callbacks; already-started asynchronous transport needs its own settlement boundary. The published language baseline is ECMAScript 2026; the current TC39 editor site describes subsequent draft work. The fifteen-second heartbeat interval remains the existing application protocol choice rather than an accessibility timing requirement.

An in-flight heartbeat can otherwise finish after playback Stop and write an older resume position. `lib/playback/heartbeat.js` now owns heartbeat scheduling and pending transport per store instance. `createPlaybackHeartbeat({ readState, send, intervalMs = 15000 })` returns `start()`, `stopTimer()`, `sendNow()`, and `drain(sessionId)`. It has no store, API, DOM, profile, fullscreen, or autoplay dependency. `sendNow()` captures and freezes the existing `{ session_id, position_ms, state, is_buffering }` body immediately; position remains floored and state remains playing/paused. Concurrent calls for the same session share its pending promise. Different sessions retain separate promises, and settled entries are removed rather than kept as an accumulating history.

`stopTimer()` clears the owned interval and invalidates stale queued timer callbacks. It leaves actual transport pending. `drain(sessionId)` returns the matching promise until fulfillment or rejection; an absent session drains immediately. Transport errors retain the existing quiet failure behavior and still release the pending entry. The caller must first stop scheduling and make playback inactive or gate explicit sends, then await that session's drain before the durable Stop request. Drain alone does not prevent later deliberate sends. Every overlapping Stop caller must await the same complete store-owned stop barrier before profile-request invalidation or navigation. Store integration and its behavioral tests remain the integrator's responsibility.

Waiting for transport preserves client request order at the cost of waiting for a slow heartbeat. Aborting a request is not evidence that its server processing has finished, so stopping the interval or discarding a response is insufficient for this ordering boundary. This module does not introduce new media-ended finalization: the existing durable Stop path retains completion/resume behavior on Close or next playback. Server-side mutation ordering remains separate contract qualification.

Tests cover the first fifteen-second tick, exact playing/paused/buffering bodies, immutable capture before transport invocation, pending deduplication, fresh reads after settlement, actual drain after timer cleanup, rejected and synchronous failure settlement, separate sessions/stores, stale interval callbacks, and unsafe-duration rejection. ### Recoverable durable release — October 7, 2026

The client now treats successful Stop acknowledgement as the boundary for leaving the player or starting a replacement stream. A transport failure is retained for explicit recovery, and the failed Promise is evicted from the session guard rather than cached permanently. The backend Stop request/response DTO remains unchanged. The prepared lost-acknowledgement test models an idempotent server reply after a committed Stop; it is not evidence that the Rust transaction and resource teardown have passed their independent tests.

The focused per-store `createPlaybackRelease({ readContext, drain, send, onChange })` service in `lib/playback/release.js` owns the immutable final session/position/cancellation record and its pending acknowledgement. It drains the matching heartbeat before submitting Stop, deduplicates pending callers, keeps failure without automatically retrying, and permits a new request only through explicit retry. Its public snapshot contains only `{ phase: 'idle' | 'releasing' | 'failed', error }`; session IDs and private paths are not presented in the notice. Successful replies stay deduplicated by the context-aware session guard. A changed context invalidates queued work before transport and ignores obsolete results.

The player facade exposes `setContext({ serverOrigin, userId })`, `reset({ preserveRelease: false })`, `stop({ retry: false })`, and `retryRelease()`. Root supplies the validated live origin/account; the same origin and account across profile changes preserves old-profile cleanup. A changed or unknown account/origin clears visible playback and retained retry work without sending old session IDs through the new context. `reset({ preserveRelease: true })` clears old Player UI/operations while retaining same-account failed cleanup for a persistent shell notice. Normal `stop()` shares pending work and rejects a retained failure without a new request; `stop({ retry: true })` is the shell/closing button's explicit retry. A new Play cannot silently release or start while failed cleanup remains, even when visible playback has already reset. Pending starts are serialized, and an exit waits for the actual late-start cancellation cleanup rather than claiming release before its session ID is known.

X and an internal navigation exit capture the current media time before physically pausing/removing the source. They retain the runtime and a polite failure/retry UI until durable release succeeds. Retry keeps the original captured body rather than replacing its position with the unloaded video's zero time. Closing Retry receives keyboard focus after failure. X defaults to the complete canonical Title destination. Internal browser history exits are cancelled while releasing and reattempt the original history delta after restoration, retaining the actual destination and native history state. Auth/profile transitions after the old Player has unmounted remain owned by the shell. Document unload is best effort: the browser can terminate requests or lose their replies, so neither an asynchronous hook nor a fifteen-second heartbeat establishes reliable final-position persistence on tab/process termination.

A failed old-session Stop before next playback does not start another session, skip an episode, resume the old source, or restart the countdown. The existing next-episode recovery remains untimed. Its explicit Play next retries the retained cleanup and then revalidates/starts the same next episode. No separate ended-finalization command was introduced; normal Close/next Stop continues to own completion accounting. The shell's PlaybackReleaseNotice presents generic polite status and explicit Retry when forced profile navigation clears the old Player; it removes no account boundary and never renders retained IDs or paths. Focus order and status announcements follow the current official [WAI focus-order guidance](https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html) and [status-message guidance](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html), rechecked October 7.
