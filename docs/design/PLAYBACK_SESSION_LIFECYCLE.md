## Research and boundaries

The current [PostgreSQL SELECT reference](https://www.postgresql.org/docs/current/sql-select.html) and [transaction isolation guidance](https://www.postgresql.org/docs/18/transaction-iso.html), reviewed October 7, 2026, establish the row-lock behavior used here: competing updates wait for the locked play-session row, then observe its committed state. The [FFmpeg stream-selection reference](https://ffmpeg.org/ffmpeg.html#Stream-selection) establishes type-based mapping and distinct simple/complex filtering. The installed `tokio-process-tools` 0.11.2 source provides handle-owned graceful termination with force-kill fallback and actual child wait; dropping a registry entry does not perform that termination.

Account authentication remains mandatory. Cleanup refers to the authenticated account's existing play session and its stored original profile, even after that same cookie session switches profiles. This does not grant the newly selected profile access to an old stream or relax profile preference, library/rating or Kids permissions. Public playback DTOs and URLs retain their existing shape.

## Atomic stop and history

The focused `playback/stop.rs` helper selects the account-bound play row `FOR UPDATE`. The first ordinary stop alone computes completion from the actual selected file's runtime, writes original-profile watch/resume/play-count and one stop event, and persists the result under the internal `duskcue_stop_result_v1` metadata key. Unrelated metadata remains intact. The history and session/event writes commit together.

Concurrent/retried ordinary stop returns the stored result without another history increment. The first accepted final position wins. A legacy already-stopped row without that internal snapshot returns its stored stop values and the current real history count without incrementing it. Cancel-before-start retains its existing eligibility rules and zero-history behavior; ordinary stop cannot reinterpret an already-cancelled session.

After persistence, stop awaits the manager's physical/cache cleanup. A cleanup failure remains an error; a retry can reuse the committed result while reattempting cleanup. No successful response is substituted for an unconfirmed encoder exit. The public response is unchanged; the snapshot is an internal serialization type, not a new public request or profile override.

Inactive profile deletion legitimately sets a retained play session's profile foreign key to null. Account-bound Stop can still finalize and release that owned session. Existing frozen results survive deletion unchanged; an active null-profile stop writes no watch/play-count data and does not reassign or recreate a profile/history row. Heartbeat, seek, preference writes and stream serving retain their profile restrictions. The prepared real DB scenario deletes a nondefault inactive profile through the authenticated API, checks both active cleanup and a persisted-stop/cache-failure retry, and verifies no history recreation or peer-account/stream access.

The shared history helper verifies that a retained file UUID still identifies a file belonging to the original media item and takes a key-share lock. Missing/deleted file identity becomes null for history; unknown duration stays unknown instead of fabricating completion. This avoids reintroducing a deleted media-file foreign key on every stop retry. Heartbeat/seek use the same reference validation.

## Heartbeat and seek ordering

`playback/heartbeat.rs` and `playback/seek.rs` take the same account-bound active play-row lock and perform their metadata/history/event changes in that transaction. Once stop wins the lock, their active-row predicate rejects later work. Once they win first, stop waits and sees their actual committed metadata. Client heartbeat draining remains useful but is not the sole protection against an HTTP observation that was aborted while the server continued.

Seek stops the old worker before allocating replacement capacity. Its replacement has an owned RAII cancellation guard until the replacement metadata/history transaction is published. An error or dropped HTTP future requests cancellation of that exact worker. Worker and session entries remain discoverable until actual exit/cache cleanup, allowing a stop that observes committed or ambiguous replacement metadata to await the real replacement. Only then are stale registry entries removed.

## Worker and cache lifecycle

The per-manager `transcoding/lifecycle.rs` actor owns one process handle, cancellation receiver, completion publication and semaphore permit. It installs drop protection before consuming stdout. Cancellation is observed while consuming stdout and while waiting for a child that has closed stdout but remains alive. Explicit termination follows the installed library's bounded graceful/forceful policy and awaits exit. The permit remains held until exit is confirmed.

Natural encoder completion releases the permit but retains cached output until the session requests cleanup. The actor owns cache removal, so cancellation of the HTTP observer does not abandon that work. Concurrent stop calls share the actual outcome. A failed attempt publishes its request generation; a manual retry waits for its new attempt instead of returning an obsolete cached error. A successful terminal outcome satisfies all subsequent stops. Manager disposal signals remaining owned actors. No PID-based global kill is used.

## Actual stream and caption arguments

The pure `transcoding/arguments.rs` helper maps the first video by type (`0:v:0`) and preserves explicit audio global index zero. Absent known audio metadata uses a type-based first-audio fallback, not an invented global index one. The playback track-selection helper prefers actual structured default audio, then the lowest valid known audio index; requested valid indices still take priority.

Caption burn-in selects the actual subtitle ordinal and retains path escaping. Its scale/pad filters are combined into that same complex graph; the conflicting separate `-vf` is removed only for the caption path. The ordinary video path retains its simple transform. This is necessary because FFmpeg does not accept simultaneous simple and complex filtering for that same output stream.
